Agent 通信：交流内容与具体问题

不同成员掌握不同信息；消息需要让接收者理解，并据此继续协作。

问题同一句“已经放好了”，可能是发送者的完成报告，也可能有当前观察支持；接收者据此采取的行动不同。
交流内容交流中具体可能出错的情况需要说清什么
事实与观察A 说“台上有个盘子”。B 不知道 A 是刚刚看见、根据之前的信息推断，还是在转述别人的话，却直接去拿。谁看到的？什么时候看到？
是观察、推断，还是转述？
历史与结果A 说“我刚才把盘子放在台上了”。之后盘子被拿走，B 仍把这条历史消息当成盘子现在还在的依据。过去做过什么？
现在是否仍然成立？
请求与分工A 请 B 把盘子拿过来，B 回复“收到”。A 把“收到请求”理解成“已经拿到”，继续安排下一步。由谁执行？
是收到、接受，还是已经完成？
提议与布局方案A 提议“先把盘子放左边，位置还可以调整”。B 转述时只留下“放左边”，其他成员以为方案已经确定。这是候选方案还是已定方案？
哪些部分还能改、还没定？
约束与依赖A 说“等汤煮好再装盘”。B 后来只收到“可以装盘”的简写，漏掉前提，汤还没好就开始下一步。行动依赖什么条件？
转述时要保留哪些前提？
产物与接口A 说“结果文件准备好了”。B 拿到的却是旧版文件，仍按新版接口继续处理，后面的步骤因此接错。哪个文件、哪个版本？
能否接到下一步所需的输入？

AutoForm：论文方法与本地复现

EMNLP 2024 · Beyond Natural Language: LLMs Leveraging Alternative Formats for Enhanced Reasoning and Communication

AutoForm 到底研究什么？

研究问题：自然语言一定最合适吗？

大模型通常用一段段自然语言思考和交流，但它也学过公式、代码、列表和表格。面对变量、关系或步骤，用这些形式表达，是否能答得更好、交流得更简洁？

具体做法：让模型自己选择并使用格式

在原有提示中加入指令：根据当前任务，选择更清晰、精确、简短的非自然语言形式，再用它推理或与其他 Agent 交流。无需重新训练模型，也不预先规定所有任务都使用同一套语法。

表达示意

“甲比乙高，乙比丙高”可以写成 甲 > 乙 > 丙。
通信时也可以按“对象—属性—证据”整理信息，供对方继续判断。

示例用于解释方法，并非论文原文。

论文如何验证？发现了什么？

一方面，在五类单模型推理任务上测答题准确率；另一方面，把资料分给不同 Agent，在三类问答任务上测答案质量与通信 token。

部分配置下，答题表现改善、交流更简短；HotpotQA 的 GPT-4 发起 + GPT-3.5 配置中，通信 token 减少 72.7%。收益随任务与模型组合变化。

本地复现：任务、过程与结果

作者代码 + Qwen3.5-27B-AWQ · 每个数据集两组各 100 题
数据集题目主要在做什么
HotpotQA综合不同段落的证据，连接中间实体或比较信息，回答一个需要多步判断的问题。
WikiHop沿文档中的实体关系寻找线索，跨多篇资料推导答案，并从候选项中确定目标实体。
NarrativeQA阅读长篇故事，结合不同段落中的人物、事件与情节，回答关于故事内容的问题。

每道题怎样完成？

① 分资料：同一问题发给两位讨论成员，各自只读到部分资料。
② 交换证据：轮流发言，补充对方缺少的信息；AutoForm 组自行选择表达格式。
③ 形成答案：答案一致或达到轮数上限后结束。
④ 本地评分：提取最终答案，与参考答案比较 EM 和答案 token-F1。

CLSR：让模型设计、积累并调用推理协议

ICML 2026 · When LLMs Develop Languages: Symbolic Protocols for Efficient Multi-Agent Reasoning

为什么研究？设计的又是什么？

研究目标：用更少的生成完成正确推理

自然语言推理常包含大量解释文字，而解题真正需要传递的，可能只是变量、条件、关系和中间结果。能否让模型自己设计更简洁的符号表达，同时保留正确解题所需的信息？

核心对象：一份可以反复使用的协议说明

论文把它称为 LSF（Language Symbolism Framework）。协议既说明符号的含义，也规定怎样组织、使用这些表达来推理。

协议内容具体说明什么
符号与词表有哪些符号，各自代表什么
组合语法符号怎样组成合法的表达
使用规则表达应遵守哪些约束与交接约定
推理映射怎样把符号表达用于推理操作
性能画像擅长哪些任务，准确率与生成成本怎样
相对 AutoForm 的推进

从“提示模型选择表达格式”，推进到“形成可复用的协议库，并根据任务选择、组合协议”。模型权重保持冻结，改进的是外部协议。

协议怎样产生？新问题来了怎样用？

① 准备阶段：提出、测试、改进，形成协议库

根据带推理过程的样例提出候选协议；在任务上检验答案是否正确、生成是否简短。通过评议、变异和重组继续改进，保留较好的协议及其性能记录，供后续问题复用。

② 解题阶段：路由器按问题选择调用方式

路由器读取题目和协议的性能画像，决定用哪些协议、按什么顺序调用，以及何时停止。

调用方式怎样完成解题
单独使用选一套适合的协议，直接求解
独立聚合多套协议分别求解，再综合它们的答案
顺序组合前一套协议的中间结果，作为后一套的输入
组合示例：物理协议 → 代数协议

先从物理条件建立方程，再交给代数协议代入求解。不同协议承担不同推理环节，可以由同一个模型调用；并不要求每套协议对应一个独立模型。

论文结果：在线生成量约为标准 CoT 的 1/3–1/6，保持准确率

这是作者在推理与问答基准上的报告。主要节省指标是在线生成量；输入与缓存成本另行分析，离线发现协议的开销单列，不能等同于全部运行成本同比下降。

A2SL-C：把消息写得更紧凑，协作会更好吗？

关注消息表达：用操作码、消息编号和正文组织请求、观察与确认。

想解决什么？具体怎么做？

出发点：减少冗余，让消息用途更明确

用简短操作码区分“请求执行”“报告观察”“确认收到”，加上消息编号和正文，检验这种表达能否改善协作。

任务：厨师与助手共同完成厨房订单

厨师掌握私有食谱，助手掌握自身工作区与技能。双方需要交流，完成准备、物品交接、烹饪与交付。

同一件事怎样表达？

消息用途表达示意

观察 OBS报告台面上有盘子
确认 ACK确认收到某条请求

含义示意；实际格式为“操作码 + 编号 + 正文”，也支持条件等消息。

AGENT COMMUNICATION / A2SLA2SL-T

A2SL-T：这句话是计划、历史，还是当前观察？

关注消息含义：区分表达地位，并核对观察与历史报告的实际来源。

为什么需要区分？怎样约束？

同样提到“放盘子”，支持的判断不同

A 说“盘子放好了”，B 准备去拿。这里要分清：是计划、过去的报告，还是当前观察？不同含义支持不同的行动。

消息内容示意接收时应怎样理解
“我准备放盘子”计划或提议，动作尚未发生
“我刚才放过盘子”历史事件，不保证盘子现在仍在
“当前台面上有盘子”当前观察，需要对应可见记录与时间
“收到，我来处理”收到或接受请求，尚不等于完成

具体做法：地位标记 + 真实来源

分别标记请求、计划、观察、历史与未核实信息。观察和历史报告引用实际可见记录；核对来源后，将对应记录提供给接收者，无依据的声明保留为未核实。

来源能够支持到哪里？

历史记录支持“之前放过”；盘子现在在哪里，仍要查当前观察。一次烹饪调用也不表示食物已经熟了。

局部行为变化与整体结果

正例：重新核对场景，避免首次错误取盘

发送方声称盘子已放好，但助手仍持盘、台面为空。来源约束保留其未核实地位；接收者复查场景、要求先放盘，避免首次错误取物。

反例：自由正文仍能误导接收者

来源显示助手仍持蛋，请求正文却写“已经放到台面”。厨师采信正文并取蛋，被原生校验拒绝；之后纠正，任务最终成功。

重复对照：整体优势尚未建立

条件完整任务成功数

本轮判断

来源约束有局部行为证据，JSON 和受控自然语言也能受益；专用 DSL 的整体优势与稳定成本收益尚未证实。

AGENT COMMUNICATION / A2SLA2SL-R

A2SL-R：一份没完成的方案，别人怎样接着补？

关注内容接续：让不同成员补全、连接和修改同一份内容，并关联实际结果。

从读懂消息，到继续处理内容

问题：交流的内容往往还没有完成

A 先提出一份方案，B 补充其中一部分，之后还可能修改。接续时需要知道：处理的是不是同一份内容？哪些地方没定？改了哪里？原来的条件还在不在？结果属于哪个版本？

设计：给内容明确身份，允许保留未定项

需要保留什么具体作用
内容身份可以明确引用同一方案或其中一个部分
尚未确定的部分模型、位置或具体产物可暂时未知，交给别人补全
关键连接关系说明两个片段的输入、输出或交接物是否相同
修改与结果归属保留明确修订；实际结果回指对应内容和证据

语言支持哪些处理？

定义一份候选内容；补全未定项或收窄条件；连接不同片段；修订已有内容；缺少定义时请求补充。

候选产物与实际产物分开

方案里写“将产生一个物品”，并不表示物品已经存在。执行之后，需要用实际观察或工具记录说明产生了什么，再补全相应引用。

真实开发例子：煮鸡蛋的跨成员接续

v0.5 · Qwen3.5-27B-AWQ · 已见开发任务
1

厨师提出准备与交接要求。具体交接物尚未确定，内容中保留未定项。

2

助手连接两个片段。明确“准备产生的物品”与“交给厨师的物品”应当是同一个未来对象。

3

助手实际取蛋、放到台面。环境推进后，当前场景中确实出现鸡蛋。

4

报告观察并补全交接内容。引用真实观察，将未定的交接物绑定到具体鸡蛋。

5

厨师引用补全后的内容继续行动。结合自身观察取蛋、入锅并烹饪，最终完成订单。

这次已经验证：开发任务中的结构接续跑通

模型生成的内容经过发送和接收，被同伴继续构造，并进入实际行动计划。该例发生了跨成员连接、补全和有来源的观察报告。

成功来自反复调试的同一任务。稳定成功率、相对同等支持自然语言的优势及额外成本仍需独立对照；该例未覆盖全部操作。后续引用解析与返修修复的离线检查，单独作为接口证据。

AGENT COMMUNICATION / A2SL交互过程

交互示例：从“请准备鸡蛋”到实际接手烹饪

厨师需要鸡蛋；助手负责准备与交接。依据 v0.5 开发记录，用中文解释消息的含义。

01 · 厨师提出准备与交接要求

请准备鸡蛋、交给我，并连接准备与交接两个片段。

def @Chef/request = Exchange@1 {
  target=@Chef/egg_prep; port=""; act="request";
  content=[@Chef/egg_prep,@Chef/egg_handoff];
  reason="Please accept the preparation and handoff for the egg and link them.";
};
request 发出请求；content 指向已定义的准备与交接内容。

02 · 助手补上“同一个物品”的关系

准备产生的物品，就是要交给厨师的物品；具体值仍未知。

compose @Assistant/egg_link =
  (@Chef/egg_prep,@Chef/egg_handoff)
connect {
  @Chef/egg_prep::?egg=@Chef/egg_handoff::?egg;
};
compose / connect 连接两个端点，尚未证明物品已经放好。

03 · 放好后报告观察，补全交接物

当前台面上观察到鸡蛋，用这次观察中的具体物品补全交接。

def @Assistant/egg_report = Report@1 {
  target=@Chef/egg_handoff; port="?egg";
  artifact=@observed/Assistant/t6/0;
  source=@evidence/Assistant/t6/0;
};
refine @Assistant/egg_handoff_bound from @Chef/egg_handoff {
  bind ?egg=@observed/Assistant/t6/0;
};
Report 关联物品与观察来源；refine / bind 补全原来的未定项。

04 · 厨师引用补全内容，继续行动

以补全后的交接内容和自身观察为依据，安排取蛋、入锅与烹饪。

Chef plan: pickup(egg, counter);
           put_obj_in_utensil(pot0); cook(pot0)
Chef basis: @Assistant/egg_handoff_bound
            @evidence/Chef/t6/0
这里是原生计划接口：basis 引用内容依据，plan 指定实际动作。

@… 是可引用的对象；?egg 是未确定的物品；::?egg 指定对象里的连接位置。代码节选真实输出、仅调整排版，省略前置定义与部分回复；第四步为原生计划接口。
