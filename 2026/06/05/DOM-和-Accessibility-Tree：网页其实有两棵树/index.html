DOM 和 Accessibility Tree：网页其实有两棵树

发表于2026-06-05|更新于2026-06-05|果冻的科普专区
|总字数:1.6k|阅读时长:5分钟

我们平时打开一个网页，看到的是按钮、文字、图片、输入框。

但在浏览器内部，网页不只是一张“画出来的页面”。浏览器会把它整理成不同的结构，其中最常被提到的两棵树，就是 DOM 和 Accessibility Tree。

如果你刚接触前端、GUI Agent、浏览器自动化，或者只是想知道“为什么看起来一样的按钮，程序和读屏软件不一定能识别”，这两个概念非常重要。

先用一句话理解

DOM 是网页的施工图，Accessibility Tree 是给辅助工具看的用户地图。

DOM 关心的是：

  • 页面用了哪些 HTML 标签
  • 这些标签怎么嵌套
  • 每个节点有什么属性、文本和事件
  • JavaScript 应该怎么找到并修改它们

Accessibility Tree 关心的是：

  • 这个东西对用户来说是什么
  • 它叫什么名字
  • 它能不能被操作
  • 它现在是什么状态

所以，DOM 更像网页的“原始结构表”。它保留了 HTML 标签、属性、层级关系，也让 JavaScript 可以读写页面。

Accessibility Tree：用户真正能理解的结构

Accessibility Tree 可以理解成浏览器从 DOM、CSS、ARIA 等信息里提炼出来的一棵“语义树”。

它主要服务于辅助技术，比如：

  • 屏幕阅读器
  • 语音控制
  • 键盘导航
  • 一些浏览器自动化和测试工具

视觉上用户看到的是 X，但在 Accessibility Tree 里，这个按钮的名字可以是“关闭”。这样读屏软件不会只读一个莫名其妙的“X”，而会告诉用户这是“关闭”按钮。

ARIA 的作用就是补充或修正可访问语义。常见的属性包括：

  • role：说明元素是什么，比如按钮、菜单、对话框
  • aria-label：给元素一个可读名称
  • aria-expanded：说明区域是展开还是折叠
  • aria-hidden：说明内容是否要从可访问树里隐藏

但 ARIA 不是万能胶。错误使用 ARIA，反而会让页面更难理解。

为什么 GUI Agent 也关心它？

如果一个 Agent 要操作网页，它可以通过很多方式理解界面：

  • 看截图，像人一样识别视觉区域
  • 读 DOM，理解页面结构
  • 读 Accessibility Tree，理解元素语义
  • 结合坐标、文本、事件和状态来决定下一步操作

其中 Accessibility Tree 很有价值，因为它把页面翻译成了更接近“用户任务”的语言。

但它也有局限：如果网页开发者没有写好语义，Accessibility Tree 可能也会很乱。一个视觉上明显的按钮，在可访问树里可能只是普通文本；一个弹窗也可能没有正确标记为对话框。

所以对 GUI Agent 来说，DOM、Accessibility Tree 和截图往往需要互相补充。

最后记住这三句话

第一，DOM 是网页代码被浏览器解析后的结构。

第二，Accessibility Tree 是浏览器翻译给辅助工具看的语义结构。

第三，看起来像按钮，不等于它在可访问树里真的是按钮。

如果你以后写前端页面，尽量使用正确的 HTML 标签。因为这不只是代码规范，也关系到用户能不能理解页面、工具能不能可靠操作页面。
