GUI Agent 架构入门：从界面感知到自主操作

发表于2026-06-05|更新于2026-06-05|果冻的理论学习
|总字数:9.6k|阅读时长:29分钟

过去我们聊 Agent，很多时候聊的是“文本世界里的 Agent”。

它读一段用户输入，拆解任务，调用搜索、数据库、代码执行器、文件系统、MCP 工具，最后把结果组织成一段文本。这个方向已经很熟悉了：ReAct、Plan-and-Execute、Reflection、多 Agent、Memory、Tool Use，这些范式本质上都围绕一个问题展开：大模型如何在文本和工具之间形成更可靠的行动链。

但 GUI Agent 不一样。

GUI Agent 面对的不是结构清晰的 API，而是一个图形用户界面。它看到的是浏览器窗口、按钮、输入框、弹窗、菜单、表格、滚动条、文件选择器、验证码、系统通知、加载动画，以及各种“人类一眼就懂、机器不一定能懂”的界面暗示。

也就是说，GUI Agent 的任务不是“回答问题”，而是“使用软件”。

比如：

  • 打开一个网页后台，登录，搜索订单，导出报表；
  • 在浏览器里查资料，把内容复制到文档里；
  • 在手机 App 里完成订票、下单、修改设置；
  • 在桌面系统中打开文件、重命名、压缩、上传；
  • 在一个没有 API 的旧系统里，通过界面把流程跑完。

这类任务真正困难的地方在于：Agent 不只是要理解用户想做什么，还要理解当前界面处在什么状态、下一步应该操作哪个控件、操作后有没有成功。如果说普通工具型 Agent 更像“会调用函数的助理”，那么 GUI Agent 更像“坐在电脑前帮你操作软件的人”。

这篇文章先不急着堆论文名，也不急着讨论某一个模型。我们先建立一张架构地图：一个基于 GUI 的 Agent，通常可以拆成哪几层？每一层解决什么问题？主流架构到底放在哪一层？为什么很多 GUI Agent 看起来很聪明，真正用起来却很容易点错、卡住、循环、误操作？

先把材料读成几句话

在学习 GUI Agent 前，可以先看几类代表性工作。

Mind2Web 关注的是 Web Agent：模型要在真实网站上完成任务，而不是在玩具网页里做选择题。它提醒我们，网页任务里有大量真实复杂性：页面结构复杂、元素很多、任务需要多步完成，而且不同网站之间差异很大。

WebVoyager 更进一步强调多模态网页操作。真实网页不只是 HTML，它还有视觉布局、图标、广告、弹窗、浮层、滚动区域。只读文本和 DOM 往往不够，模型需要同时利用截图和页面结构。

SeeClick 把重点放在 GUI grounding 上，也就是“看见界面之后，能不能点准”。这件事听起来简单，其实是 GUI Agent 的核心瓶颈之一。模型知道“下一步要点提交按钮”还不够，它必须知道提交按钮在屏幕上的具体位置。

OSWorld 则把问题放到真实操作系统里评测。它不是只看网页，而是让 Agent 在真实桌面环境中完成跨应用任务。这类基准说明了一件事：GUI Agent 要想真正使用电脑，就必须面对文件系统、浏览器、办公软件、系统设置等复杂环境。

UI-TARS 这类工作代表了更 native 的 GUI Agent 方向：把截图、语言指令和动作空间放到一起训练，让模型直接面向图形界面生成操作动作。

OpenAI 的 Computer Use 和 Anthropic 的 computer use 方向，则从产品化角度展示了另一个事实：GUI Agent 不是单纯模型能力，而是一整套运行时系统。它需要截图、动作接口、浏览器或虚拟机环境、安全确认、日志和失败恢复。

所以，学习 GUI Agent 时，我认为最重要的不是先背系统名字，而是先抓住一个判断：

GUI Agent 本质上是一个运行在图形界面上的闭环控制系统。

它不是“加了截图的聊天机器人”，也不是“更聪明的 RPA”。它至少包含观察、理解、定位、决策、执行、反馈和评估几个部分。下面我们用五层架构来拆。

GUI Agent 的基本闭环

一个最小可用的 GUI Agent，通常会反复执行这样的循环：

比如用户说：“帮我登录后台，下载昨天的销售报表。”

Agent 不能直接回答“好的”。它要真的做事：

  1. 打开目标网站；
  2. 观察登录页；
  3. 找到账号输入框；
  4. 输入账号；
  5. 找到密码输入框；
  6. 输入密码；
  7. 点击登录；
  8. 等待页面跳转；
  9. 判断是否登录成功；
  10. 找到报表菜单；
  11. 选择日期；
  12. 点击导出；
  13. 等待文件下载；
  14. 检查文件是否存在；
  15. 向用户报告结果。

这里每一步都可能失败。

按钮可能没加载出来，页面可能弹出二次验证，日期控件可能不是普通输入框，下载按钮可能在滚动区域下面，文件可能被浏览器拦截，登录可能失败但页面没有明显错误提示。

这就是 GUI Agent 和普通问答 Agent 的关键区别：普通问答 Agent 的失败通常表现为“回答错了”；GUI Agent 的失败可能表现为“点错了、删错了、提交错了、卡在某个页面上不知道发生了什么”。

所以 GUI Agent 架构必须比普通 Agent 更重视运行时闭环。它不是一次推理完成任务，而是在界面反馈中不断修正。

五层架构总览

我会把 GUI Agent 拆成五层：

这五层不是严格的代码目录划分，而是一种理解方式。

环境层决定 Agent 在哪里运行；感知层决定它看见什么；Grounding 层决定它能不能把意图落到具体控件上；决策层决定它下一步怎么做；安全与评估层决定它能不能可靠、可控地完成任务。

如果只看模型，很容易误以为 GUI Agent 的核心问题是“大模型够不够聪明”。但从工程视角看，很多失败其实出在分层之间：

  • 环境层没有提供稳定截图；
  • 感知层漏掉了关键弹窗；
  • Grounding 层点错了按钮；
  • 决策层陷入重复尝试；
  • 评估层误判任务已经完成；
  • 安全层没有拦住高风险动作。

下面逐层展开。

第一层：环境层

环境层回答的是：Agent 到底运行在哪里？

GUI Agent 不是飘在空气里的模型。它必须连接到一个可以被观察、可以被操作的环境。这个环境可能是浏览器，也可能是完整桌面系统，也可能是手机模拟器，还可能是一个远程虚拟机。

常见环境有几类。

第一类是浏览器环境。

这是目前最常见的 GUI Agent 场景。浏览器里有大量真实任务：搜索、登录、表单填写、后台管理、网页应用、数据下载、在线文档、邮箱、CRM、工单系统。浏览器环境的好处是可控性比较强，开发者可以拿到 DOM、URL、页面标题、网络请求、cookie、localStorage，也可以通过 Playwright、Selenium、Chrome DevTools Protocol 这类工具执行动作。

浏览器环境里，Agent 可以不只是“看截图”，还可以读页面结构。比如它可以知道某个按钮的文本、属性、CSS selector、坐标、是否可见。这使得 Web Agent 往往比纯桌面 Agent 更容易做稳定。

第二类是桌面环境。

桌面环境更接近“真正用电脑”。Agent 面对的是整个操作系统，包括浏览器、文件管理器、终端、办公软件、聊天软件、图片工具、压缩软件、系统设置。桌面环境的优势是覆盖面广，很多没有 API 的软件也能通过界面操作；缺点是复杂度高，状态空间大，动作风险也更高。

桌面环境通常依赖截图、鼠标键盘动作、窗口管理、accessibility API、OCR 和文件系统检查。比如 OSWorld 这类基准之所以重要，就是因为它把 Agent 放到了更真实的电脑环境里，而不是只在网页里完成简化任务。

第三类是手机环境。

手机 App 的 GUI Agent 通常运行在 Android 模拟器、真实设备或远程手机上。它可以通过 UIAutomator、Accessibility Service、Appium 等方式读取控件树，也可以通过截图理解界面。手机环境的特点是交互动作更多样：点击、长按、滑动、返回、输入、权限弹窗、底部导航、系统分享面板等。

手机 GUI Agent 很适合研究“真实 App 自动化”，因为很多 App 没有开放 API，也不可能通过 DOM 操作，只能像用户一样点屏幕。

第四类是远程桌面或虚拟机环境。

这类环境常用于评测和安全隔离。Agent 不直接操作用户本机，而是在一个沙箱、虚拟机、VNC 或浏览器容器里完成任务。它的好处是即使 Agent 出错，也不至于破坏用户真实环境；同时可以记录完整轨迹，方便复盘和评估。

环境层看似只是“运行在哪里”，但它实际上决定了上层架构的天花板。

如果环境只给截图，Agent 就必须走视觉路线；如果环境能给 DOM 和 accessibility tree，就可以走结构化路线；如果环境能提供动作回放、文件检查、网络日志，就可以做更强的评估和恢复。

所以设计 GUI Agent 的第一步，不是选模型，而是问清楚：

  • 我是在网页、桌面、手机还是虚拟机里操作？
  • 我能拿到截图吗？
  • 我能拿到 DOM 或控件树吗？
  • 我能执行哪些动作？
  • 我能观察到动作之后的真实结果吗？
  • 出错后能不能回滚或重置环境？

这些问题决定了后面四层怎么设计。

第二层：感知层

感知层回答的是：Agent 怎么“看见”界面？

人看 GUI 很自然。我们看到一个页面，会自动理解标题、按钮、输入框、层级、分组、焦点、颜色、警告、禁用状态、当前选中的 tab。机器没有这么自然，它需要把界面变成可推理的输入。

主流感知方式可以分成三类：结构化感知、视觉感知、混合感知。

结构化感知

结构化感知就是尽量不让模型只看图片，而是读取界面的结构。

在网页里，结构化信号包括 DOM、HTML、ARIA 属性、可见文本、元素坐标、按钮类型、输入框类型、label、placeholder 等。在桌面和手机里，结构化信号可能来自 accessibility tree、UIAutomator、Appium、系统无障碍接口。

结构化感知的优点很明显。

第一，它更精确。一个按钮在 DOM 里就是一个 button，可能还有文本、id、class、role、aria-label。模型不需要从像素里猜测它是不是按钮。

第二，它更便宜。文本结构比截图更小，处理成本更低。

第三，它更适合执行。拿到元素 ID 或 selector 之后，可以直接触发点击，而不是估算坐标。

但结构化感知也有问题。

很多现代界面并不总是结构友好。Canvas 画出来的界面、游戏、远程桌面、图片化按钮、Electron 应用、复杂自定义组件，都可能让 DOM 或控件树失真。还有一些元素虽然存在于 DOM 中，但被遮挡、不可见、不可点击。模型如果只相信结构，就可能点击到用户看不见的元素。

所以结构化感知很重要，但不能神化。

视觉感知

视觉感知就是让 Agent 看截图。

截图的优势是“所见即所得”。不管是网页、桌面软件、手机 App、远程桌面，只要用户能看到，截图就能捕捉到。视觉感知可以理解布局、图标、颜色、遮挡、弹窗、加载状态、选中状态，也能处理很多结构化接口拿不到的信息。

这也是为什么近两年 GUI Agent 方向越来越依赖多模态模型。SeeClick、UI-TARS、computer use 这类方向，本质上都把截图作为重要输入，让模型从界面图像中理解下一步操作。

视觉感知的难点也很直接。

首先是成本和延迟。截图比文本大，多模态模型调用更贵，响应更慢。

其次是精确定位。模型看懂“登录按钮在右下角”还不够，它要输出精确坐标。一个按钮可能只有几十像素高，点偏一点就无效。

再次是状态理解。截图是瞬间状态，很多动态信息不容易表达，比如页面正在加载、某个按钮刚刚变成可点击、某个输入框获得焦点、某个下载任务已经完成。

所以视觉感知覆盖面更广，但稳定性更难。

混合感知

工程上最实用的路线通常是混合感知。

也就是同时使用截图、DOM、OCR、accessibility tree、坐标、窗口信息、文件系统状态等多种信号。

混合感知的优势在于互补。

DOM 告诉你“页面上有哪些元素”；截图告诉你“用户实际看到了什么”；OCR 告诉你“图片里写了什么”；坐标告诉你“动作应该落在哪里”；文件和网络日志告诉你“操作是否产生了真实结果”。

但混合感知也带来系统复杂度。

不同信号之间可能冲突。DOM 里有按钮，但截图里被弹窗盖住；OCR 识别出一段文字，但它不是可点击元素；元素坐标来自浏览器视口，但执行动作发生在远程桌面坐标系里；页面滚动后，旧坐标失效。

所以感知层不只是“把信息给模型”，还要做信息对齐：

  • 哪些元素当前可见？
  • 哪些元素真的可点击？
  • 文本和控件之间是什么关系？
  • 截图坐标、浏览器坐标、远程桌面坐标是否一致？
  • 页面变化后哪些缓存需要刷新？

这层做得越好，决策层就越轻松。很多所谓“模型不聪明”的问题，本质上是感知输入太乱。

第三层：Grounding 层

Grounding 层回答的是：Agent 怎么把自然语言意图落到具体界面动作上？

这层非常关键，因为 GUI Agent 的许多失败都发生在这里。

用户说“点击登录”。决策层可能也判断下一步应该点击登录。可问题是：登录按钮到底是哪一个？

页面上可能有：

  • 顶部导航里的“登录”；
  • 弹窗里的“登录”；
  • 第三方登录区域；
  • 灰色不可点击的登录按钮；
  • 被遮挡的登录按钮；
  • 移动端折叠菜单里的登录按钮；
  • 当前视口外的登录按钮。

Grounding 层要做的就是把“登录按钮”变成一个可执行目标：

如果是网页，Grounding 的结果可能是 selector 或 element handle。如果是桌面截图，Grounding 的结果可能是坐标。如果是手机 App，可能是 resource-id、text、bounds，或者 tap 坐标。

Grounding 可以分成几个子问题。

第一个是目标识别。

模型要判断哪个控件符合意图。比如“日期选择器”“导出按钮”“保存设置”“展开高级选项”，这些名称未必直接出现在界面文本里，需要结合上下文理解。

第二个是坐标定位。

在 screenshot-only 架构里，模型往往要直接输出 (x, y)。这要求模型不仅理解语义，还要有很强的空间定位能力。SeeClick 这类工作之所以重要，就是因为它把 GUI grounding 作为核心能力来训练和评测。

第三个是可操作性判断。

不是看起来像按钮就能点。按钮可能被禁用，可能被 loading 状态覆盖，可能需要先勾选协议，可能在滚动容器里只露出一部分，可能点击区域比视觉区域更小。

第四个是动作参数生成。

GUI 动作不只有点击，还包括输入、滚动、拖拽、快捷键、选择、复制粘贴、文件上传。不同动作需要不同参数：

第五个是执行后校验。

点击之后，页面有没有变化？输入之后，文本是否真的进入了输入框？下载之后，文件是否真的出现？如果没有变化，是点错了、页面慢、还是动作无效？

这就是为什么 Grounding 不能只看作“坐标预测”。它其实是自然语言意图、界面语义、空间位置和动作执行之间的桥。

如果感知层负责“看见”，Grounding 层负责“点准”。

第四层：决策层

决策层回答的是：Agent 怎么决定下一步做什么？

这一层最接近我们平时说的 Agent 架构。ReAct、Planner-Executor、Reflection、Skill/RPA、多 Agent、端到端 VLA，大多都可以放在决策层讨论。

但在 GUI Agent 里，决策层有一个特殊约束：它的每个决定都必须落到真实界面动作上。普通 Agent 调错一个搜索词，最多结果不好；GUI Agent 点错一个按钮，可能提交表单、删除文件、发出消息。

所以 GUI Agent 的决策层不能只追求“聪明”，还要追求“稳”。

ReAct：边看边做

ReAct 的基本形式是：

ReAct 很适合 GUI Agent，因为 GUI 操作天然就是一步一步反馈的。每次动作之后，界面会变化；Agent 再根据新观察决定下一步。

它的优点是灵活。

如果登录后出现二次验证，Agent 可以根据新观察调整。如果搜索结果为空，Agent 可以换关键词。如果按钮没出现，Agent 可以滚动或等待。

但 ReAct 的问题也明显。

第一，长任务容易漂移。每一步都局部决策，可能走着走着忘了整体目标。

第二，成本高。每点一步都调用模型，会增加延迟和费用。

第三，容易循环。比如页面没变化，Agent 可能反复点击同一个按钮。

第四，格式和动作空间要严格约束。模型如果输出了不可执行动作，运行时就会失败。

所以 ReAct 适合短链路、局部反馈强的 GUI 任务，但不适合完全承担长流程规划。

这种架构的好处是长任务更清楚。Planner 保持全局目标，Executor 处理界面细节。任务失败时，也可以回到某个子任务继续，而不是从头开始。

它特别适合企业办公自动化。因为企业流程通常有清晰步骤：登录、筛选、导出、上传、审批、发送。高层步骤相对稳定，低层界面可能有变化。

但 Planner-Executor 也有难点。

第一，计划可能过时。Planner 一开始制定的步骤，执行过程中可能被弹窗、权限、异常状态打断。

第二，Planner 和 Executor 的接口要设计好。Planner 不能只说“处理一下报表”，它要给 Executor 可执行的子目标；Executor 也不能只说“失败了”，它要反馈失败原因。

第三，什么时候重新规划很关键。每一步都重新规划太贵；完全不重新规划又容易卡死。

所以比较好的做法是：Planner 提供粗粒度路线，Executor 做局部 ReAct，遇到异常再触发 replanning。

Reflection：执行后自我检查

Reflection 在 GUI Agent 里也很重要，但它和文本任务里的 Reflection 不完全一样。

文本任务中，Reflection 常常是让模型检查答案质量。GUI Agent 中，Reflection 更像是检查执行轨迹：

  • 我刚才点击后页面有没有变化？
  • 这个页面是不是任务目标页面？
  • 我是不是点错了相似按钮？
  • 当前状态是否和计划一致？
  • 是否需要回退、刷新、等待或换路径？

Reflection 的价值在于提高鲁棒性。GUI 任务充满不确定性，如果没有反思机制，Agent 很容易把“动作发出去了”误认为“任务完成了”。

但 Reflection 也有成本。它会增加模型调用和延迟。如果每一步都反思，系统会很慢。所以更实用的方式是按风险触发：

  • 页面长时间无变化；
  • 动作连续失败；
  • 即将执行高风险操作；
  • 任务完成前做最终检查；
  • 观察结果和预期不一致。

也就是说，Reflection 不一定是每一步都执行的固定流程，而是 GUI Agent 的故障诊断能力。

Skill / RPA 增强：把稳定流程沉淀下来

GUI Agent 如果每次都从零看界面、从零规划、从零点击，成本会很高，也不稳定。

现实中很多 GUI 任务是重复的：

  • 登录某个系统；
  • 打开某个菜单；
  • 导出某类报表；
  • 上传文件；
  • 创建工单；
  • 在固定表单里填字段；
  • 从某个页面复制数据。

这些流程可以沉淀成 Skill 或 RPA 脚本。

Skill / RPA 增强架构的思路是：让大模型负责理解任务和处理异常，让稳定流程交给可复用技能。

例如用户说：“帮我导出昨天的销售报表。”

Agent 可以判断这属于已有技能：

技能内部可能用 Playwright、Selenium、Appium 或系统脚本完成稳定点击。模型不需要每次重新推理按钮在哪里。

这种架构非常适合生产环境。因为生产环境追求稳定和成本，而不是每一步都炫技。

它的缺点是维护成本。界面改版后，技能可能失效；流程变了，脚本要更新；不同用户权限不同，技能要处理分支。

所以 Skill/RPA 增强不是替代 GUI Agent，而是和 GUI Agent 互补。一个好的系统应该允许：

  • 常见稳定流程走技能；
  • 新任务或异常情况走模型推理；
  • 技能失败后回到视觉/结构化观察；
  • 成功轨迹反过来沉淀为新技能。

这也是 GUI Agent 从 demo 走向真实使用的关键。

多 Agent：把规划、视觉、执行、验证拆开

复杂 GUI Agent 还可以做多 Agent 分工。

比如：

  • Planner Agent：负责拆解任务；
  • Perception Agent：负责解释截图和控件树；
  • Grounding Agent：负责选择目标元素和坐标；
  • Executor Agent：负责调用动作接口；
  • Verifier Agent：负责判断任务是否完成；
  • Safety Agent：负责拦截高风险操作。

这种设计的好处是职责清楚。每个 Agent 可以用不同 prompt、不同模型、不同工具，甚至不同评估标准。

比如视觉理解可以用强多模态模型，执行层可以用确定性脚本，验证层可以结合文件系统和页面状态，安全层可以用规则和模型共同判断。

但多 Agent 也会引入复杂度。

第一，通信成本高。每一层都要传递状态，容易变慢。

第二，错误归因困难。任务失败时，很难判断是 Planner 错、感知错、Grounding 错，还是执行接口错。

第三，系统调试复杂。多个 Agent 之间可能互相甩锅，或者输出粒度不匹配。

所以多 Agent 不适合一开始就上。它更适合任务复杂、风险高、需要审计和分工的场景。

端到端 VLA / Native GUI Agent：从截图到动作

还有一类更前沿的方向，可以叫端到端 VLA 或 Native GUI Agent。

VLA 是 Vision-Language-Action。放到 GUI Agent 里，就是模型接收截图和语言指令，然后直接生成 GUI 动作。

例如：

UI-TARS 这类工作就更接近这个方向。它试图让模型原生理解 GUI，并直接输出鼠标键盘动作，而不是完全依赖外部规则和 DOM。

这个方向的优势是泛化潜力大。只要界面能显示出来，模型就可能操作。它不依赖某个网站的 DOM，不依赖某个 App 的控件树，也不需要每个流程都手写脚本。

但它也有很大挑战。

第一，训练数据难。需要大量真实 GUI 轨迹，包括截图、指令、动作、结果。

第二，评估难。GUI 任务不是单步分类，必须看最终状态。

第三，安全难。模型直接输出动作，如果缺少约束，风险很高。

第四，可解释性弱。端到端模型点了某个位置，不一定能清楚解释为什么。

所以我更倾向于把 Native GUI Agent 看成底层能力，而不是完整系统。真正可用的 GUI Agent 仍然需要环境、感知、Grounding、安全、评估、日志、技能和人类确认。

  • 这个任务是短流程还是长流程？
  • 是否有稳定重复步骤？
  • 是否需要视觉理解？
  • 失败后能不能重试？
  • 动作风险有多高？
  • 是否需要人类确认？

不同问题对应不同架构组合。

第五层：安全与评估层

安全与评估层回答的是：怎么知道 Agent 做对了？怎么防止它乱做？

这层在 GUI Agent 里非常重要，因为 GUI Agent 会真实改变外部环境。

普通聊天 Agent 说错一句话，用户可以不采纳。GUI Agent 如果点错按钮，可能提交订单、删除文件、发送邮件、修改配置、转账付款。这就是为什么 computer use 类产品都非常强调权限、确认和隔离。

安全与评估层至少包括几个部分。

权限边界

系统必须定义 Agent 能操作什么、不能操作什么。

比如：

  • 是否允许访问某些网站？
  • 是否允许下载文件？
  • 是否允许上传文件？
  • 是否允许删除文件？
  • 是否允许发送消息？
  • 是否允许提交表单？
  • 是否允许支付、购买、转账？

这些不能完全交给模型自觉。应该有明确规则、allowlist、denylist 和动作拦截。

人类确认

高风险动作应该让人确认。

比如：

  • 删除；
  • 支付；
  • 提交申请；
  • 发送邮件或消息；
  • 修改生产配置；
  • 授权第三方；
  • 上传敏感文件。

GUI Agent 的安全原则应该是：低风险动作可以自动化，高风险动作必须确认。

日志和轨迹

GUI Agent 必须记录轨迹。

包括：

  • 每一步观察到什么；
  • 模型为什么决定下一步；
  • 选择了哪个目标；
  • 执行了什么动作；
  • 动作结果是什么；
  • 是否触发安全确认；
  • 最终如何判断完成。

没有日志，GUI Agent 很难调试，也很难信任。任务失败时，开发者必须能复盘：是看错了、想错了、点错了，还是执行环境出问题了。

任务完成判断

GUI Agent 最大的问题之一是“自以为完成”。

比如 Agent 点击了导出按钮，就报告“已导出”。但真实情况可能是：

  • 文件还在生成；
  • 下载被浏览器阻止；
  • 导出失败但页面提示很小；
  • 文件下载了但格式不对；
  • 下载的是空报表；
  • 日期选错了。

所以评估层不能只看动作是否执行，还要看最终状态是否满足任务目标。

沙箱隔离

GUI Agent 最好运行在沙箱里。

浏览器容器、虚拟机、远程桌面、手机模拟器，都是常见方式。沙箱的意义是限制损害范围，同时提供可重置环境。

对于研究和评测，沙箱可以让任务反复运行；对于生产系统，沙箱可以隔离敏感资源；对于用户个人电脑，沙箱可以避免 Agent 误操作真实文件。

安全与评估层不是最后才补的功能。它应该从一开始就参与架构设计。

三条主线：看见、点准、做完

讲完五层之后，我们可以把 GUI Agent 的难点压缩成三句话：

第一，能不能看见。

这对应感知层。Agent 是否能理解当前界面？是否知道有哪些控件？是否能识别弹窗、错误提示、加载状态？

第二，能不能点准。

这对应 Grounding 层。Agent 是否能把自然语言目标映射到正确元素或坐标？是否能处理滚动、遮挡、相似按钮、禁用状态？

第三，能不能做完。

这对应决策层和评估层。Agent 是否能完成长流程？是否能从失败中恢复？是否能判断任务真的完成？是否能避免高风险误操作？

很多 demo 只展示“看起来会操作”。但真正有用的 GUI Agent，需要在这三件事上同时过关。

GUI Agent 和传统 RPA 的关系

谈 GUI Agent 很容易绕不开 RPA。

RPA 也是操作界面。它可以点击按钮、填写表单、导出报表。那 GUI Agent 和 RPA 有什么区别？

我理解二者不是替代关系，而是连续谱。

传统 RPA 更像确定性脚本。它适合稳定流程、固定界面、明确规则。比如每天早上打开系统，选择固定菜单，导出固定报表。只要界面不变，RPA 很可靠、成本低、可审计。

GUI Agent 更像带有理解和恢复能力的操作者。它适合界面有变化、任务描述更自然、流程有分支、需要根据反馈判断下一步的场景。

GUI Agent 和普通 Tool Agent 的区别

普通 Tool Agent 调用的是 API。API 有函数名、参数、返回值、错误码。虽然也会失败，但接口边界比较清楚。

GUI Agent 调用的是界面。界面不是为机器设计的，而是为人设计的。它有视觉暗示、布局习惯、动态变化、遮挡关系、非标准组件。

第二，状态观察不同。

第三，错误反馈不同。

API 调用失败可能返回 400、403、500。GUI 操作失败可能什么都不发生，也可能出现一个很小的红字提示。

第四，安全风险不同。

Tool Agent 的权限通常在 API 层定义。GUI Agent 可能通过界面访问到很多隐含能力，比如删除、发送、付款、授权。

所以 GUI Agent 不是简单地把工具从 API 换成鼠标键盘。它需要一整套更强的观察、定位、评估和安全机制。

学习路径

如果要系统学习 GUI Agent，我建议按下面顺序来。

第一步，理解基本闭环。

先不要急着看模型。先把 observe、plan、ground、act、verify 这个循环想清楚。任何 GUI Agent 都绕不开这条链。

第二步，学习 Web Agent。

Web Agent 是最好的入门场景，因为浏览器既有真实复杂性，又能提供 DOM、截图、网络、文件下载等丰富信号。可以从 Mind2Web、WebVoyager、SeeAct 这些方向理解网页任务为什么难。

第三步，学习 GUI grounding。

重点看模型如何从界面描述中选择目标元素，或者从截图中预测坐标。SeeClick 这类工作可以帮助理解“点准”为什么是独立问题。

第四步，学习 computer use / desktop agent。

这时再看 OSWorld、UI-TARS、OpenAI Computer Use、Anthropic computer use，会更容易理解它们为什么强调截图、动作空间、沙箱、评估和安全。

总结

GUI Agent 的目标，是让智能体从“会回答”走向“会操作”。

它的本质不是聊天，也不是简单脚本，而是一个运行在图形界面上的闭环控制系统。

这套系统至少包含五层：

环境层决定它在哪里操作；
感知层决定它看见什么；
Grounding 层决定它能不能点准；
决策层决定它下一步怎么做；
安全与评估层决定它能不能可靠地做完。

其中决策层可以容纳很多主流 Agent 架构：ReAct 适合边看边做，Planner-Executor 适合长任务，Reflection 适合失败恢复，Skill/RPA 适合稳定流程，多 Agent 适合复杂分工，端到端 VLA 则代表更原生的 GUI 操作模型方向。

但最终决定 GUI Agent 是否可用的，不只是模型是否强，而是整个架构是否闭环。

它要看得见、点得准、做得完、可恢复、可评估、可审计、可控制。

这也是 GUI Agent 最有意思的地方：它把大模型从文本世界带回了真实软件世界。过去我们通过 API 让模型调用工具，现在我们开始让模型直接面对人类每天使用的图形界面。这个方向一旦成熟，很多没有 API、没有自动化接口、只能靠人手操作的软件流程，都可能被重新组织。

但也正因为它真的能操作外部世界，我们不能只用“模型智能”来理解它。更准确的理解方式是：GUI Agent 是模型、界面、动作、反馈、安全和评估共同组成的系统工程。

先理解这张架构图，再去看具体论文和产品，就会清楚很多。
