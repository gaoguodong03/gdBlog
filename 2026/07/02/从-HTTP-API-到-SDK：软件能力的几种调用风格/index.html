SDK 到底是什么：五种常见的软件调用风格

发表于2026-07-02|更新于2026-07-03|果冻的理论学习
|总字数:3k|阅读时长:9分钟

最近在讨论项目里的一个模块怎么接入。导师提了一句：“这里最好用 SDK 接入，不要直接 HTTP 接入。”

这句话乍一听很简单，但真要写进方案里，就会发现它背后有一个更大的问题：

一个软件能力，到底可以用什么“风格”交给别人使用？

比如文件管理能力。它可以上传文件、下载文件、删除文件、列出文件、生成预览链接。那其他代码要怎么使用它？

可以直接发 HTTP 请求。
可以调一个 SDK。
可以在后端内部调 Service。
可以按插件规则扩展它。
也可以通过命令行操作它。

这些都不是简单的“写法不同”，而是不同的能力暴露方式。

这篇文章就专门聊聊 SDK，以及和它经常放在一起比较的几种调用风格：

  • HTTP API
  • SDK / Client Library
  • Service Layer
  • Framework / Plugin
  • CLI

先说 API、HTTP API 和 SDK

这三个词很容易混在一起。

API 是最宽泛的词，意思是“接口”。它描述的是：这个系统提供什么能力，别人怎么调用。

HTTP API 是 API 的一种实现方式。它通过 HTTP 请求暴露能力。

SDK 是 Software Development Kit，软件开发工具包。它不是单个接口，而是一套给开发者使用的工具。

SDK 和 HTTP 不是完全对立的东西。很多 SDK 的底层仍然是在发 HTTP 请求，只是它不让你每次都亲手拼 URL、header、body 和签名。

所以老师说“用 SDK，不要用 HTTP”，很多时候真正想表达的是：

不要让业务代码到处写裸 HTTP 请求。应该有一层更稳定、更好用的封装。

1. HTTP API：最直接的接口

HTTP API 是最常见的能力暴露方式。

它的风格是：你给我一个 URL、一个请求方法、一组参数，我返回给你结果。

例如文件上传：

它的好处非常明显：直接、开放、通用。

只要你的系统能发 HTTP 请求，不管你是 Python、Java、Go、JavaScript，还是另一个外部系统，都可以接。

所以 HTTP API 很适合：

  • 前端调用后端
  • 外部系统集成
  • 微服务之间通信
  • 提供开放平台接口
  • 跨语言、跨进程、跨机器调用

但 HTTP API 的麻烦也很真实。

调用者要自己处理：

  • 请求地址怎么拼
  • token 怎么放
  • 上传文件用什么格式
  • 超时和重试怎么做
  • 错误码怎么解释
  • 返回 JSON 怎么解析
  • 接口版本变了怎么办

如果只是写一个 Demo，这些都还好。
但如果正式项目里十几个地方都在手写 HTTP 请求，就会很快变成“哪里都能调，哪里都不好改”。

HTTP API 的关键词是：

直接，但调用者要承担更多细节。

2. SDK / Client Library：把接口包装得更像工具

SDK 风格更像是把一堆底层能力打包成一个开发者容易使用的工具箱。

同样是文件上传，用 SDK 风格可能变成：

看起来只是少写了几行代码，但本质变化很大。

调用者现在关心的是：

  • 我要上传文件
  • 我要拿下载链接
  • 我要删除文件

而不是：

  • 请求方法是 POST 还是 PUT
  • Content-Type 是什么
  • token 应该放 header 还是 query
  • 401、403、404 分别怎么处理

一个比较完整的 SDK 通常会包含这些东西：

组成 作用
Client 入口 保存配置、鉴权信息、服务地址
领域方法 比如 upload、delete、list_files
数据模型 比如 FileInfo、UploadResult
错误封装 把 HTTP 错误变成更清楚的业务异常
默认策略 超时、重试、分页、日志、版本兼容
示例文档 让开发者知道怎么快速接入

所以 SDK 的价值不是“看起来更高级”，而是它改善了开发者体验。

它把“协议细节”包装成“业务动作”。

HTTP API 像是在说：

请按文档构造这个请求。

SDK 像是在说：

你直接调用这个方法就行。

这就是 SDK / Client Library 风格的核心：

把底层接口封装成稳定、易用、面向开发者的方法集合。

这里顺便区分一下 SDK 和 Client Library。

很多时候二者会被混用。严格一点说，Client Library 更轻，主要负责封装远程调用；SDK 更完整，除了 Client，还可能包含工具、示例、类型定义、调试能力、脚手架、文档等。

但在日常项目讨论里，如果老师说“SDK 接入”，大概率指的就是：

用一层官方或项目内封装好的 Client，而不是到处裸写 HTTP。

3. Service Layer：项目内部的服务层

Service Layer 和 SDK 有点像，但它通常不是给外部开发者用的，而是给项目内部代码用的。

比如文件管理功能和你的业务系统就在同一个后端里，这时你可能不会让内部模块互相发 HTTP 请求，而是直接调用服务层：

这就是 Service Layer 风格。

它的重点不是“对外接入”，而是“内部复用”。

典型结构大概是：

外部用户可以通过 HTTP API 访问文件能力；但系统内部的订单模块、用户模块、审批模块，不一定也要去发 HTTP 请求。

它们可以直接调用 FileService。

这有一个非常实际的好处：内部逻辑不会被 HTTP 细节污染。

比如业务代码不需要知道：

  • 文件接口 URL 是什么
  • HTTP 状态码怎么映射
  • 请求体怎么序列化
  • 内部模块之间是否需要 token

所以，如果文件管理模块还没有独立成外部服务，先设计 Service Layer 往往比一上来就设计 HTTP Client 更自然。

4. Framework / Plugin：不是你调用它，而是它调用你

前面几种风格，大多是“我主动调用某个能力”。

Framework / Plugin 风格就不太一样了。

它更像是：

你按照框架规定的方式写代码，然后框架在合适的时机调用你。

这种风格常见于：

  • Web 框架
  • 插件系统
  • 编辑器扩展
  • 工作流引擎
  • CMS 系统
  • AI 工具平台

它的核心是“控制反转”。

这种方式适合做生态和扩展。

比如文件管理模块可以提供这些插件点：

  • before_upload
  • after_upload
  • before_delete
  • after_delete
  • on_preview

这样别人就能在不改核心代码的情况下扩展能力。

Framework / Plugin 的关键词是：

框架定义规则，开发者按规则补充能力。

它比 SDK 更“强势”。SDK 只是给你工具；Framework 会规定你怎么组织代码、什么时候执行、能接在哪些位置。

CLI 是 Command Line Interface，命令行接口。

它不是给业务代码高频调用的首选方式，但它非常适合给人和脚本使用。

  • 自动化脚本
  • CI/CD 流程
  • 临时排查问题

这五种风格到底怎么选？

可以先记住一句话：

HTTP API 解决“怎么跨网络访问”，SDK 解决“怎么让开发者好用”，Service Layer 解决“项目内部怎么复用”，Framework / Plugin 解决“别人怎么扩展你”，CLI 解决“人和脚本怎么操作”。

放到文件管理场景里，大概是这样：

风格 面向谁 典型用法 适合解决什么问题
HTTP API 外部系统、前端、其他服务 POST /files/upload 跨网络、跨语言调用
SDK / Client Library 其他开发者、其他项目 client.upload(file) 降低接入成本
Service Layer 同一个后端项目内部 file_service.upload(file) 内部业务复用
Framework / Plugin 扩展开发者 after_upload(file) 插件化、生命周期扩展
CLI 人、脚本、运维流程 filectl upload a.pdf 调试、自动化、批处理

它们不是互斥关系。

所以不要把问题简化成“SDK 和 HTTP 谁更好”。

更准确的问题应该是：

当前这个模块，是要给谁用？用在什么边界上？调用者应该看到多少底层细节？

回到“SDK 接入而不是 HTTP 接入”

如果有人建议“用 SDK 接入，不要用 HTTP 接入”，可以把这句话翻译成更工程化的版本：

不要让业务代码直接散落书写 HTTP 请求。应该把远程能力封装成一个稳定的 Client，让调用者通过方法调用完成业务动作。

如果这个模块还在同一个后端项目里，也可以继续补一句：

如果文件管理还没有独立部署，内部调用可以先走 Service Layer；等它需要开放给外部系统时，再提供 HTTP API；如果其他项目要频繁接入，再在 HTTP API 之上封装 SDK / Client Library。

这就比简单说“SDK 比 HTTP 好”准确得多。

因为 SDK 不是魔法。

SDK 的本质是：

把一个能力包装成开发者更容易理解、更不容易用错、更适合长期维护的调用入口。

小结

最后再用一版更口语化的方式记：

  • HTTP API：把能力放到网上，谁会发请求谁就能调。
  • SDK / Client Library：把请求细节藏起来，让开发者像调本地方法一样使用能力。
  • Service Layer：项目内部别绕远路，直接沉淀业务服务。
  • Framework / Plugin：你别乱调我，按我的规则写扩展，我到时候来调你。
  • CLI：给人和脚本一个顺手的命令行入口。

如果只记一句：

HTTP API 是入口，SDK 是包装，Service 是内部能力，Plugin 是扩展机制，CLI 是操作工具。

理解了这几个风格，再听到“这个模块用 SDK 接入”时，就不会只停留在名词上，而是能继续追问：这个 SDK 是给谁用的？底层接什么？它和 HTTP API、Service Layer 的边界在哪里？

原文：The 8 Levels of Agentic Engineering — Bassim Eledath 作者：Bassim Eledath AI 的编程能力正在超越我们驾驭它的能力。这就是为什么所有那些拼命刷 SWE-bench 分数的努力，并没有与工程领导层真正关心的生产力指标同步。Anthropic 团队用 10 天就上线了 Cowork，而另一个团队用着同样的模型却连一个 POC（概念验证）都搞不定——区别在于一个团队已经弥合了能力与实践之间的差距，而另一个还没有。 这个差距不会一夜之间消失，而是分等级逐步缩小。总共 8 个等级。读到这篇文章的大多数人可能已经过了前几个等级，而你应该迫不及待地想达到下一个——因为每升一级都意味着产出的巨大飞跃，而每次模型能力的提升都会进一步放大这些收益。 你应该在意的另一个原因是多人协作效应。你的产出比你想象的更依赖于队友的等级。假设你是 7 级高手，晚上睡觉时后台智能体就在帮你提好几个 PR。但如果你的代码仓库需要一位同事审批才能合并，而这位同事还停留在 2 级，仍在手动审查 PR，那你的吞吐量就被卡死了。所以帮队友升级，对你自己...
