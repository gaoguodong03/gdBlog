LSP 和 AST：编辑器是怎么变聪明的

发表于2026-07-29|更新于2026-07-29|果冻的科普专区
|总字数:1.9k|阅读时长:6分钟

前两天在翻一些工具的文档时，看到两个反复出现的缩写：LSP 和 AST。网上的解释要么太学术，要么太简略——“AST 是抽象语法树””LSP 是语言服务器协议”——但真正的问题一直没解开：

编辑器是怎么知道你写错了、还能自动补全、甚至跨文件跳转到定义的？

顺着这个疑问往下挖，我发现这两件事其实是一条线索的两端：一头是代码的结构化理解，另一头是编辑器和分析引擎之间的标准化沟通。这篇文章就从你的编辑器出发，讲讲 LSP 和 AST 到底是什么。

AST：从”字符串”到”树”

先做个思想实验。你写了一行代码：

这行字对你来说意味着”1 加上 2 乘以 3 的结果”。但对计算机来说，它最初只是一个字符串——一堆字符排在一起。字符串本身不产生任何语义。

为了让计算机理解这段代码，编译器/解释器会先做一件关键的事情：把它解析成一棵树。

这棵树就是 AST（Abstract Syntax Tree，抽象语法树）。每个节点代表一个语法元素：数字字面量、运算符、变量名、函数调用……树的结构反映了代码的语法逻辑。

AST 的实际用途

AST 是几乎所有现代开发工具的基石。几个你天天在用的例子：

工具 做了什么
ESLint 遍历 AST，检查”这里有个未使用的变量””那里用了 == 而不是 ===“
Prettier 重新排版 AST 节点，而不是靠正则乱修格式
Babel / TypeScript Compiler 把现代语法（JSX、?.、??）的 AST 转译成兼容旧浏览器的 AST
代码搜索（如 Sourcegraph、AST-grep） 搜”所有调用 foo 且参数是字符串 "bar" 的地方”，而不是匹配注释里的巧合

关键在于：AST 让工具能区分”不同含义的相同字符串”。比如一个变量叫 name 和一个函数叫 name()，在 AST 里它们是不同类型的节点，用正则搜 name 会把它们混在一起，而基于 AST 的搜索不会。

LSP：把语言智能搬出编辑器

有了 AST，我们可以写一个程序来分析 JavaScript 代码。但问题来了：这个分析程序放在哪？

传统做法是每个编辑器自己集成一套分析引擎——VS Code 内置一套、Vim 内置一套、IntelliJ 内置一套。每套都得单独开发，互相不兼容，而且每种语言都得做一遍。

这就是 LSP 要解决的问题。

LSP 的核心思路

LSP（Language Server Protocol，语言服务器协议） 是一个标准化的通信协议，规定了编辑器（客户端） 和语言分析引擎（服务器） 之间该聊什么、怎么聊。

语言服务器运行在独立的进程中，实时分析你项目里的所有文件（当然会用到 AST）。编辑器通过 LSP 发请求，服务器回结果。

你在 VS Code 里见到的这些功能，背后都是 LSP 的请求：

功能 你在 UI 上的操作 LSP 请求
自动补全 敲几个字符，弹出建议列表 textDocument/completion
悬停类型提示 鼠标悬停在变量上 textDocument/hover
跳转到定义 按住 Cmd 点击函数名 textDocument/definition
查找所有引用 右键 → Find All References textDocument/references
重命名 F2 重命名符号 textDocument/rename
实时语法错误 看到红色波浪线 textDocument/publishDiagnostics

每个请求都带着文件路径、光标位置、触发上下文。语言服务器基于它维护的 AST 和符号表来回答。

LSP 为什么能火

LSP 在 2016 年由微软提出（和 VS Code 一起推出），很快成为行业标准。原因是它解决了一个多方博弈的困境：

  • 编辑器作者：不再需要为每种语言写一套分析工具，只要实现一次 LSP 客户端就能对接所有语言
  • 语言团队：不用为每个编辑器单独写插件，开发一个 LSP 服务器就能覆盖 VS Code、Neovim、Emacs、JetBrains……
  • 用户：换编辑器时不会失去语言智能，体验可以做到接近无缝迁移

举个例子：你用 VS Code 写 TypeScript，切到 Neovim 装个 typescript-language-server 插件，照样能补全、跳转定义、看类型——因为底层是同一个语言服务器在工作。

按下快捷键的那一刻，发生的事情：

  1. VS Code（LSP 客户端） 发一条 textDocument/definition 请求给 Pyright（Python 语言服务器），参数包括 file_b.py 的路径和光标在第 2 行的位置

  2. Pyright（语言服务器） 收到请求，取出 file_b.py 的 AST，定位到调用的 greet 节点。但它并不知道 greet 在哪定义，所以它会在自己的符号表里查找——这个符号表是它持续扫描整个项目后建立的。符号表找到 greet 定义在 file_a.py 第 1 行

  3. Pyright 返回结果：file_a.py 第 1 行第 5-10 字符

  4. VS Code 收到结果，把光标跳过去，顺便高亮

整个过程通常在几十毫秒内完成，而你只是按了一下快捷键。

两个人的视角

换个角度来理解也挺有意思：

AST 像是编译器眼中的代码。 编译器不关心代码在屏幕上看起来什么样，它只在乎代码的结构是否正确：这段代码是表达式还是语句？这个符号是变量还是函数？括号是不是配对的？

LSP 像是你的编辑器雇佣了一个话不多的专家坐在后台。 你不需要自己装编译器、跑分析脚本，只需要发消息给后台专家，他就会把分析结果告诉你。

AST 是那位专家用来理解代码的知识图谱，LSP 是你和专家之间的对话协议。

总结

概念 是什么 帮你做什么
AST 代码被解析成的树形结构 让工具能理解代码的语法语义，而不是当纯文本瞎搜
LSP 编辑器和语言服务器之间的标准化协议 让你在编辑器里获得 IDE 级别的智能感知（补全、跳转、错误提示）

两个概念单独拎出来都不复杂，但把它们放在一起，就是现代编辑器体验的底层架构。下次你需要搭一套新的开发环境，或者想给自己的工具链加点”语言感知”，这两个概念就是最基础的设计锚点。

补充一句：LSP 不只是大语言模型（LLM）时代的东西，它是传统的程序分析架构。不过，随着 LLM 驱动的编程助手兴起（Copilot、Cursor、Codex），LSP 也在和 AI 补全逐渐融合——那是另一个话题了。
