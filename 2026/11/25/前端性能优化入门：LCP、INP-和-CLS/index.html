前端性能优化入门：LCP、INP 和 CLS

发表于2026-11-25|更新于2026-11-25|果冻的科普专区
|总字数:2.1k|阅读时长:6分钟

你用手机打开一个商品页。页面框架很快就出来了，商品主图却等了几秒才显示。好不容易能看了，点一下「切换规格」，按钮半天没反应。再往下滑，顶部突然插进一条优惠横幅，刚要点的按钮被挤走了。

这三个问题都可以用一句「网页有点卡」来形容，但它们分别发生在加载、交互和布局三个环节。Google 的 Core Web Vitals（核心网页指标）用 LCP、INP 和 CLS 来衡量这三种体验。我们就拿这个商品页，看看三个指标各在测什么，遇到问题应该从哪儿查起。

指标 用户感受到的问题 良好 较差
LCP（Largest Contentful Paint，最大内容绘制） 首屏主要内容迟迟没出现 ≤ 2.5 秒 > 4 秒
INP（Interaction to Next Paint，交互到下一次绘制） 点了以后迟迟没有画面反馈 ≤ 200 毫秒 > 500 毫秒
CLS（Cumulative Layout Shift，累积布局偏移） 正在看或准备点的内容突然移位 ≤ 0.1 > 0.25

线上评估时，每个指标都看真实访问的第 75 百分位（P75），手机和电脑分开统计。比如手机端 LCP 的 P75 是 2.4 秒，就意味着至少约 75% 的有效样本在 2.4 秒以内看到了 LCP 元素。三个指标的 P75 都达到「良好」，才算通过 Core Web Vitals 评估。Web Vitals 官方说明

1. LCP：商品主图什么时候出现？

LCP 从页面开始加载计时，记录视口内最大的符合条件的内容元素何时绘制出来。商品页里这个元素可能是商品主图，文章页里也可能是标题或一块正文。手机和电脑的视口大小不同，同一个页面的 LCP 元素也可能不同。排查时可以先用 Chrome DevTools 的 Performance 面板录制一次页面加载，点开 LCP 标记确认具体元素。

假设商品主图就是 LCP 元素，可以把等待时间拆成四段。每段慢，要查的东西都不一样。

卡在哪一段 怎么判断 怎么优化
等 HTML 的第一个字节（TTFB） Network 里文档请求的首字节来得晚 查服务端渲染、数据库查询和重定向。对适合缓存的公开页面考虑 CDN 或服务端缓存。
等浏览器开始请求主图 HTML 已开始返回，主图请求却很晚才发出 让初始 HTML 就带上 <img> 和图片地址。首屏主图避免用 loading="lazy"，确认它是关键资源后可试用 fetchpriority="high"。
等主图下载 请求发出得早，但图片传输时间长 用 srcset 和 sizes 按屏幕尺寸提供图片，压缩图片或改用 WebP、AVIF，再用瀑布图检查传输时间。
等浏览器把主图画出来 图片已经下载完，LCP 标记还晚了很久 查主线程、阻塞渲染的样式，以及主图是否等客户端脚本执行完才显示。优先移走首屏用不到的脚本和样式。

比如主图在 1 秒时就下载完了，但轮播组件要等到 3 秒才初始化，初始化之前整块区域一直隐藏。这时把 JPEG 换成 WebP，主图可能下载得更快，用户却还是要等 3 秒。直接让首张图随 HTML 显示，再加载轮播增强功能，才能缩短这里的等待。Optimize LCP

2. INP：点「切换规格」后，多久能看到反馈？

INP 观察用户在页面停留期间的点击、触摸和键盘操作，用其中接近最慢的一次交互来反映页面的响应速度。一次交互从用户操作开始计时，到浏览器绘制下一帧为止。比如点「切换规格」以后，按钮可以先变成选中状态，库存随后再更新。INP 关注的是前一次画面反馈，库存接口的完整耗时要另外测。

在 Performance 面板录制一次卡顿的操作，查看 Interactions 轨道，可以把延迟拆成三段。

  • 输入延迟。用户点了按钮，浏览器还没开始运行事件处理函数。如果主线程正在执行分析脚本或初始化组件，可以延后非必要脚本，把耗时计算拆成小任务，或者把能独立运行的纯计算交给 Web Worker。
  • 处理耗时。事件处理函数已经开始，但它顺手筛了几千条数据、改了多个组件的状态。先更新按钮状态，把次要工作延后，并让出主线程给浏览器渲染。只把函数声明成 async，其中的同步代码仍会占用主线程。
  • 呈现延迟。事件处理函数已经跑完，浏览器还在算样式、布局和绘制。检查这次更新牵动了多少 DOM 节点，比如切换一个规格时是否重建了整张商品推荐列表，再缩小更新范围。

同一个按钮有时秒回，有时卡半秒，录制时要复现用户操作的时机。比如一进页面就点一次，再等页面稳定后点一次。只有第一次卡的话，可以对照看看它是否撞上了页面初始化时的长任务。Optimize INP

3. CLS：准备点的按钮为什么突然挪了？

CLS 衡量的是意外的布局偏移。浏览器会根据受影响的视口面积和元素移动的距离给单次偏移打分，再取累计分数最高的一组。相邻偏移间隔小于 1 秒、整组持续时间最多 5 秒。点击或按键等操作后 500 毫秒内发生的布局偏移通常会被排除，比如点开「规格详情」时内容立即向下展开。异步请求过了一会儿才返回、把内容突然顶开，就仍有可能计入。

商品页里，优惠横幅如果要等接口返回才插进顶部，可以从第一帧就给它留好位置。图片、视频和嵌入组件也是一样，先让浏览器知道它们要占多大的空间。比如 1200 × 800 的商品图可以这样写：

如果再用 CSS 设置 max-width: 100% 和 height: auto，图片可以随容器缩放，浏览器也能在文件下载前按 3∶2 的比例留出空间。卡片骨架屏同样需要尽量接近最终内容的高度，否则切换时还是会跳。要是文字在网页字体加载后突然换行，可以先选字宽接近的备用字体，再按需要调整字体度量。

在 DevTools 的 Performance 面板查看 Layout Shifts 轨道时，注意区分「哪个元素挪了」和「谁把它挤走了」。如果高亮的是购买按钮，可以沿着页面往上看，检查是否有横幅、图片或字体刚好在同一时间改变了尺寸。Optimize CLS

实际优化时怎么测？

  1. 先看线上用户遇到什么。 用 PageSpeed Insights 查看真实用户数据，留意报告显示的是当前 URL 还是整个站点，以及手机和电脑哪端更差。样本不足时，可以用 web-vitals 在自己的站点采集数据，按页面类型和设备查看 P75。PageSpeed Insights 说明 · web-vitals
  2. 再用开发者工具复现。 保持相同的设备模拟、网络和缓存条件。看 LCP 就录页面加载，看 INP 就把切换规格这样的操作录进去，看 CLS 就多录一会儿，覆盖滚动、异步内容和字体加载。Lighthouse 的加载测试会给出 TBT（总阻塞时间），可以用来定位加载期间的长任务。要测真实交互的 INP，仍要实际操作页面。
  3. 改完重跑同一个场景。 比如给优惠横幅预留位置后，重录一次它出现的过程，确认对应的偏移消失。上线后继续看同一类页面的 P75。PageSpeed Insights 的真实用户数据覆盖过去 28 天，刚发布的版本会和窗口内的旧数据混在一起。
