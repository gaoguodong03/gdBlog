从 HTTP 请求到接口文档：OpenAPI、Redoc 和 Swagger UI 是什么？

发表于2026-11-25|更新于2026-11-25|果冻的科普专区
|总字数:2.1k|阅读时长:6分钟

如果我想把「晚上记得发周报」存在一个自己取名叫 test 的字段里，可以吗？

可以。只是「字段」这个词可能指三个地方。它可能是浏览器发出去的 JSON 字段，也可能是数据库里的一列，还可能是接口文档里的一条参数说明。它们可以都叫 test，做的事却各不相同。

我们就从这七个字怎么离开浏览器讲起。下文用自己设计的便签接口举例，最后再看看博客里的「随手传」实际是怎么接上 Supabase 的。

1. 点下「保存」之后，浏览器发了什么？

假设我设计了一个接口 POST /notes，用来创建便签。我规定调用的人把文字放进一个叫 test 的字段。前端就会把输入框里的字放进一个 JSON 对象，再通过 HTTP 发给服务器。

用 HTTP/1.1 的写法，可以把这条请求展开来看。下面的域名和接口都是演示用的。HTTP/1.1 消息格式

  • 第一行说的是「用 POST 方法调用 /notes」。
  • 接下来是请求头。Host 指出请求发给谁，Content-Type 告诉服务器用 JSON 来解析正文。
  • 空行后面是请求体。这里传的才是你刚刚输入的内容。这个 JSON 用 UTF-8 编码后是 32 字节，浏览器通常会自己处理长度，无需手填。

平时我们口头说「发了一个数据包」，在这里，具体要看的就是这条 HTTP 请求，以及它里面装数据的 请求体。到了网络传输层，这条请求的字节还可以分成多段发送。写前端的时候，我们通常只需要关心请求发到哪里、用什么方法、带哪些数据。

2. 收到 test 以后，服务器怎么保存？

服务器读到请求体，先把那串 JSON 解析出来，再取 test 对应的值。接下来怎么存，由接口的实现决定。比如数据库里有一列叫 content，照样可以把 test 传来的文字存进去。

请求字段 test
传过来的值 晚上记得发周报
数据库列 content

写入成功后，服务器再发回来一条 HTTP 响应。比如用 201 Created 表示创建成功，响应体里给出刚生成的便签 ID。

如果代码和数据库都由你设计，叫 test、content 或 body 都可以。真正需要对齐的是前端和接口的约定。假如接口规定 test 必填，前端却只发了 content，服务器就可能返回一个错误。接口一多，光靠口头说「这个字段记得填」就容易出错。

3. OpenAPI 把接口的用法写下来

刚才那条 HTTP 请求，可以回答「我这一次发了什么」。另一个开发者第一次来接入时，他要问的是「以后每一次调用，我应该怎么发」。

OpenAPI 是一种描述 HTTP 接口的标准。 我们可以用 YAML 或 JSON 写下来，把接口路径、请求方法、字段类型和返回值讲清楚。下面是一份对应前面例子的 OpenAPI 文件。OpenAPI 3.1 规范

这里有个容易看混的细节。requestBody.content 是 OpenAPI 用来列出请求体格式的固定写法。往下到 properties.test，才是我给接口设计的字段。至于 example 里的那句话，只是展示请求长什么样。换个用户粘贴另一段话，实际请求里的值自然也会变。

这份文件的价值在于，工具也能读懂「test 必填，是字符串」。同一份说明可以拿去生成网页、校验接口定义，或者生成客户端代码。后端有没有按约定处理，还要看实际实现和测试。

4. Redoc 和 Swagger UI 各自怎么用这份说明？

假设同事想查 POST /notes 到底要传什么。把上面的文件交给 Redoc，他就可以在网页目录里点开「创建便签」，看到 test 的类型、必填标记、示例和 201 的响应结构。几十个接口也可以用同样的方式浏览。文件更新后重新构建，页面就会反映新的说明。Redoc 开源仓库 · 在线示例

换成 Swagger UI，同事除了查说明，还可以点 Try it out，把示例改成 {"test":"明早开会"} 再点 Execute。这时浏览器会向配置好的服务器发一条真的 HTTP 请求。只要目标服务器可访问、浏览器允许跨域请求，并且调用者有必要的权限，服务器就会按接口逻辑处理。如果点的是创建接口，测试也可能真的写入一条记录。上面的 api.example.com 是演示地址，实际试用时需要换成自己的 API 地址。Swagger UI 官方文档

我现在想做什么 对应的东西
把一段具体的文字发给后端 HTTP 请求，文字在 JSON 请求体里
约定所有调用者都用 test 字段 OpenAPI 接口说明
让开发者方便查字段和示例 Redoc，也可以用 Swagger UI
在文档页里发个请求看看结果 Swagger UI 的试用功能
让另一台电脑也能读到这段文字 后端服务和数据库

所以 Swagger UI 里确实可以「填字段、发请求、看返回」。你点了执行之后，真正接收和保存这段文字的，还是自己的 API。

5. 我们的「随手传」为什么用 Supabase？

随手传需要的是：我在一台电脑上保存一段文字，换一台电脑登录后还能读到它。我们把页面放在博客里，浏览器通过 Supabase 的 JavaScript SDK 发请求。文字保存在项目的 PostgreSQL 数据库里，文件放在 Supabase Storage，登录由 Supabase Auth 处理。随手传 · Supabase 文档

用刚才的例子来对照，Supabase 把这些层串在了一起。它提供接收 HTTP 请求的 Data API 和保存记录的数据库。Data API 底层的 PostgREST 还能根据暴露出来的数据库结构生成 OpenAPI 描述，Supabase 控制台有自己的 API 文档页面来展示项目的接口和调用示例。这一层和 Redoc、Swagger UI 的文档展示功能类似。随手传的页面调用的是 SDK。Supabase Data API · PostgREST 的 OpenAPI 文档 · Supabase Studio 文档组件

自己搭一份时，先注册或登录 Supabase，创建一个自己的项目。项目会自带一个独立的 PostgreSQL 数据库，然后在里面建自己的表和字段。比如想通过自动生成的 Data API 直接往便签表传 test，就可以建一个 test 文本列，再配置登录和行级权限，让使用者只访问自己的记录。如果还要传文件，就在项目里建一个 Storage bucket 并配置访问权限。Supabase 控制台的账号用于管理项目，随手传页面里的账号用于登录应用。Supabase 入门 · 数据库与行级权限

当初看到 Swagger UI 能填表单、发请求，我会想到能不能直接拿它做随手传。顺着这条请求走一遍就好理解了。开发者查文档时关心的是「test 怎么传」，我打开随手传时关心的是「刚才那段话还在不在」。一个网页可以帮人试接口，另一个网页可以把登录、保存和读取做成每天都顺手的操作。它们可以调用同一个后端。
