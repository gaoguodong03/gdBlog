书童四九：把专家、技能和工具组织成可复用的 AI 工作空间

发表于2026-10-20|更新于2026-10-22|果冻的奇妙小工具
|总字数:2.6k|阅读时长:7分钟

写一篇需要查资料、反复修改、最后配图的文章，往往要经历好几个环节：向一个工具描述需求，到另一个工具找资料，再把结果复制回来写作。修改到一半，还需要重新交代背景，或者到聊天记录里寻找上一个版本。

我开发书童四九时，希望把这些步骤放进一个可以持续工作的空间：用户维护自己的专家、技能、模型和工具，在同一个会话中完成任务，并把中间材料和最终结果保存为文件。

书童四九是一个支持私有化部署的 AI Agent 应用搭建与运行平台。 它提供角色配置、主持人与专家协作、Skill 管理、工具调用和会话工作区，适合把经常重复的工作整理成可复用应用。

从一次协作会话认识书童四九

进入系统后，主要有三个入口：工作空间、资源中心和设置。日常使用发生在工作空间；需要增加能力时进入资源中心；默认主持人、环境变量和沙箱等配置放在设置中。

下面这张截图来自已有的协同写作会话。用户提出文章需求后，主持人把当前任务交给文档合著专家；专家回复中带有大纲和正文的文件入口，右侧工作区保存对应文件。

图 1：协作会话：主持人分派任务，文档合著专家交付阶段文稿，右侧保存会话文件。

这张图展示的是一次任务的阶段成果：正文已经形成，仍在等待用户反馈。资料核查、正文审阅和最终确认继续由使用者把关。

先理解四种资源：场景、专家、Skill 和工具

这几个概念分别回答不同的问题：

资源 回答的问题 使用例子
场景 这项工作需要哪些角色，怎样协作？ 伴学研讨、简历协作
专家 谁负责当前任务？ 文档合著专家、简历评估专家
Skill 当前任务按什么方法完成？ 先确认大纲、逐章写作、保存版本
工具 通过什么动作访问数据或产生结果？ MCP 工具、HTTP API、工作区文件操作、技能脚本

模型则为主持人和专家提供理解、生成与工具选择能力。资源中心可以维护多个模型配置，并为角色选择合适的模型。

这种组织方式让新增应用有了一条清楚的路径：准备需要的 Skill 和工具，配置专家，再把专家组合进场景。

配置专家：明确职责，再绑定能力

进入 资源中心 → 专家，可以新建角色，填写名称、描述、系统提示词，选择模型并绑定技能。保存后，该专家就能被邀请到会话，或者加入一个场景。

以文档合著专家为例，它负责大纲、正文、修订和润色，描述中会明确写出工作范围。需要检索公开资料或生成图片时，由承担相应职责的专家处理。

图 2：专家配置：维护角色名称、模型、职责说明、系统提示词和绑定技能。

这里的角色分工会影响实际执行：主持人选择本轮专家；专家根据绑定的 Skill 确定本轮工作方法，再使用允许的工具完成任务。一个专家绑定多个 Skill 时，运行时会进行本轮 Skill 选择。

对于反复出现的工作，角色配置也能减少重复说明。用户不必每次重新输入整套写作规范，只需要交代这一次的目标、材料和特殊要求。

管理 Skill：把工作方法保存下来

进入 资源中心 → 技能，可以编辑 SKILL.md，并维护 references/、assets/、scripts/ 等配套文件。技能页同时展示工具声明和 Python 依赖，便于检查运行条件。

当前的“文档合著”Skill 就是一种流程型技能。它约定先确认文档目标，再生成大纲；章节逐步推进，阶段文稿保存到工作区，需要反馈时停下来等待用户。

图 3：文档合著 Skill：工作步骤、阶段确认和成果保存规则都可以在页面中维护。

这类技能不一定需要额外脚本。它的作用是让工作过程可重复、可调整，也让“已经完成什么、还在等待什么”有更明确的依据。

如果任务包含表格处理、批量转换等确定性操作，可以在 Skill 中提供脚本。平台通过统一执行入口调用脚本；脚本能力还需要相应的依赖和沙箱环境。实际使用前，先检查技能页的依赖提示，再到 设置 → 沙箱 维护运行环境。

使用场景：保存一套专家组合

逐个配置专家之后，可以在 资源中心 → 场景 保存它们的组合、场景说明和主持人配置。

例如，当前的简历协作场景包含候选人事实建档、简历生成、简历评估和定向优化四类专家。场景说明定义各自职责，主持人结合当前阶段和用户输入选择下一位处理者。

图 4：场景配置：维护应用目标、主持人和协作规则，让一组专家能够重复用于同类任务。

以这个场景的配置为例，先整理候选人事实，再生成简历；评估阶段形成报告和变更计划，用户决定后再应用修改。哪些步骤需要确认、每一步交付什么，由场景规则与对应 Skill 共同约定。当前这套场景面向 Markdown 简历流程。

对于使用者来说，场景把一组配置变成了工作入口。在会话输入框旁点击 场景，选择已配置场景，就能带入对应专家组合和主持人配置。

日常怎么用：从任务到文件交付

准备好模型和所需资源后，可以按下面的方式开始：

  1. 在工作空间点击 新建会话，根据任务选择场景，或通过角色按钮邀请专家。
  2. 输入目标、读者、材料和交付格式。需要指定角色时，可以使用 @ 提及主持人或专家。
  3. 点击 文件 上传材料或引用已有工作区文件，让任务指向明确输入。
  4. 查看主持人分派、专家回复和工具执行信息；专家提出必要问题时，补充材料或确认当前成果。
  5. 打开产物入口或右侧文件面板，检查、编辑和下载结果。

以写作为例，一个清楚的任务可以这样描述：

请根据我上传的材料写一篇面向工程团队的功能介绍，约 1500 字，使用 Markdown。先给大纲，确认后再写正文；涉及资料中没有的数据时，请标出需要补充的信息。

这里的交付格式、确认节点和材料范围都很具体，专家更容易判断当前任务的完成条件。

文件面板是这条流程的重要部分。点击文件后，可以直接预览内容，进入编辑，或者下载到本地。资源中心的“文件”入口还能按会话查看已有工作区。

图 5：会话文件预览：对话记录与实际文件并排展示，便于检查阶段成果并继续修订。

聊天记录保留协作过程，工作区保存可继续使用的内容。后续修改可以引用明确的文件路径，让材料和版本更容易定位。

从个人配置到可迁移应用

当一套配置已经适合某类任务，可以导出 ZIP 资源包，在其他账号中导入复用。导入前会展示对象、依赖和冲突，平台处理场景、专家、Skill 和工具之间的引用关系。

这使得应用复用可以围绕完整资源关系展开。迁移之后仍需检查目标环境的模型连接、密钥变量和沙箱依赖，确保外部服务可用。

我在这个项目中重点解决的工程问题

在用户看见的配置与对话背后，我主要围绕协作运行、能力接入和结果交付完成端到端开发：

用户可见的功能 对应的工程实现
主持人与专家轮流处理任务 结构化调度字段、阶段状态与 Skill 接续机制
不同专家使用不同能力 按本轮 Skill 装配工具，统一处理结构化 Tool Calling
对话中产生可访问文件 会话工作区、产物校验和预览下载接口
配置脚本型能力 OpenSandbox 执行环境、只读 Skill 挂载与路径访问约束
查看执行过程 SSE 输出、工具日志和异常信息
私有化使用 用户资源隔离、数据持久化与 Docker / 1Panel 部署

实现过程中，一个持续的问题是怎样让“模型说完成了”与“系统确实产生了结果”对应起来。因此，工具结果、真实文件、阶段状态和交接信息都需要进入执行链路，而不能只依赖一段自然语言回复。

目前，模型驱动的调度仍需要结合具体场景验证，阶段确认的体验也有继续打磨的空间。会话和检查点的保存提供了状态基础；服务重启后的后台任务恢复仍有边界，需要继续完善。

对我来说，书童四九的开发重点，是把一次 AI 对话延伸为可以配置、协作、检查并交付文件的工作过程。使用者可以从一个专家开始，再逐步把自己的常用方法整理成 Skill 和场景。

原文：The 8 Levels of Agentic Engineering — Bassim Eledath 作者：Bassim Eledath AI 的编程能力正在超越我们驾驭它的能力。这就是为什么所有那些拼命刷 SWE-bench 分数的努力，并没有与工程领导层真正关心的生产力指标同步。Anthropic 团队用 10 天就上线了 Cowork，而另一个团队用着同样的模型却连一个 POC（概念验证）都搞不定——区别在于一个团队已经弥合了能力与实践之间的差距，而另一个还没有。 这个差距不会一夜之间消失，而是分等级逐步缩小。总共 8 个等级。读到这篇文章的大多数人可能已经过了前几个等级，而你应该迫不及待地想达到下一个——因为每升一级都意味着产出的巨大飞跃，而每次模型能力的提升都会进一步放大这些收益。 你应该在意的另一个原因是多人协作效应。你的产出比你想象的更依赖于队友的等级。假设你是 7 级高手，晚上睡觉时后台智能体就在帮你提好几个 PR。但如果你的代码仓库需要一位同事审批才能合并，而这位同事还停留在 2 级，仍在手动审查 PR，那你的吞吐量就被卡死了。所以帮队友升级，对你自己...
