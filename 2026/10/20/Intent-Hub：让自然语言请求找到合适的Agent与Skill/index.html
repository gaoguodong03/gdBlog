Intent Hub：让自然语言请求找到合适的 Agent 与 Skill

发表于2026-10-20|更新于2026-10-22|果冻的奇妙小工具
|总字数:2.7k|阅读时长:8分钟

一个系统里有了多个 Agent 或 Skill，接下来就会遇到能力选择问题：用户说“我的快递到哪里了”，应该交给物流查询；说“包裹已经超过预计送达时间”，更适合进入配送延误处理。

这两句话都与快递有关，真正决定入口的却是任务边界。能力越来越多时，把判断逻辑分散在提示词和业务代码里，维护和排查都会变得困难。

Intent Hub 把能力选择做成一套可配置、可测试、可持续维护的语义路由服务。 管理者在网页中维护意图名称、职责描述、正负语料和阈值；上层系统通过 API 提交自然语言，获取匹配的 route_key，再调用对应能力。

先看界面：一条意图怎样表示一种能力

管理台的主要入口包括 意图实体、测试、诊断、设置和日志。从“意图实体”页开始，可以看到每种能力的名称、路由标识、阈值、正向语料、负向语料和同步状态。

下面是当前环境中的两条相关路由：

意图 route_key 职责边界
订单物流查询 order.logistics_tracking 查询位置、轨迹、进度和预计送达时间
订单配送延误 order.delivery_delay 处理超时、长期未更新和运输停滞问题

图 1：意图实体列表：把职责、样本、阈值和同步状态放在同一处管理。

名称主要用于阅读，route_key 用于程序识别能力。上层业务可以维护路由键与具体 Agent、Skill 或接口的映射，使能力选择和实际执行分别演进。

新增或编辑意图：先写清“什么请求应该进来”

点击 新增，或在已有实体旁点击 编辑，即可维护路由配置。

一条可用的意图至少需要明确名称、路由标识和典型请求。职责描述最好同时说明支持范围与边界。例如，配送延误的描述中明确写出“处理超过预计送达时间、物流长期不更新”等情况，并排除普通位置查询。

图 2：意图编辑表单：维护名称、路由标识、业务描述、匹配阈值与正向语料。

正向语料是“应该匹配到这里”的请求，如“快递迟迟没有送到”“为什么配送一直卡在中转站”。负向语料则用来表达容易混淆、但不属于本意图的请求。

在当前配置中，配送延误路由把“我现在的快递到哪里了”列为负例。它与延误问题语义接近，却没有表达异常或超时，正好适合说明两种能力的区别。

页面还提供 AI 生成语料、推荐负例和通过 SKILL.md 生成草稿的入口。这些功能帮助准备配置，生成内容仍需要人工检查，保存并完成索引同步后才用于后续匹配。

在线测试：结果应该能解释

配置完成后进入 测试 页，输入一句自然语言并点击测试，可以查看候选意图、路由键和匹配分数。下面两组结果来自本文准备期间的实际页面操作，使用的是已有配置。

普通查询：负例帮助排除相近能力

输入：

我现在的快递到哪里了

结果只返回“订单物流查询”，显示的向量相似度为 0.9375。

图 3：普通物流查询的实测结果：只返回 order.logistics_tracking。

查看这次请求的路由记录还能看到：配送延误路由虽然也有正例候选，但命中了它自己的负例，被排除后没有进入最终结果。

这里的负例机制是根据负例相似度和对应阈值排除路由，并非简单地从正例得分中减去一个分数。它让“内容相关”和“职责适用”之间多了一层边界判断。

延误请求：普通路由可以返回多个候选

再输入：

我的订单超过预计送达时间了

当前配置返回两个合格候选：配送延误排第一，分数为 1.0000；物流查询排第二，分数为 0.8300。

图 4：延误请求的实测结果：两个候选均通过阈值，配送延误排在首位。

这个结果也说明了使用时需要理解的边界：普通预测会返回按分数排序的合格路由列表。上层系统需要决定采用首选、增加澄清，或执行自己的进一步判断。

此外，这条延误请求本身就是已有正向语料。分数为 1.0000 可以说明当前配置的匹配行为，不能据此推导对新表达的准确率。页面上的分数是向量相似度，也不能解释成“回答正确的概率”。

反馈与诊断：让路由边界逐步清楚

测试结果下方提供正负反馈按钮。反馈会把输入补充到对应路由的正例或负例，随后通过同步链路更新索引。它调整的是样本和配置；每次修改后，都应复测原问题和相关的正确请求，避免把边界收得过窄。

当能力较多、误命中原因不明显时，可以进入 诊断 页查看语义重叠。

图 5：语义重叠诊断：当前结果提示物流查询和配送延误存在路由级重叠。

当前页面显示，这两条订单路由的区域相似度约为 86.3%，但没有检测到明显的样本冲突对。这个信息适合提示管理者检查职责和样本，并不表示有 86.3% 的请求会被误路由。

诊断同时提供分布图入口，用 UMAP 将高维样本投影到二维，辅助观察聚集和重叠。实际路由仍在原始向量空间中完成，判断质量需要回到具体输入、候选分数与职责边界。

一个实用的维护顺序是：先发现问题请求，再查看候选和排除原因，调整描述、样本或阈值，等同步成功后回归测试。修复建议可以帮助提出方案，最终还要通过问题样本验证。

保存之后，为什么还要看同步状态

Intent Hub 将业务配置与向量索引分开维护：SQLite 保存配置、版本与同步任务，Qdrant 保存用于检索的派生索引。

新增或编辑意图后，本地配置先保存，后台再处理索引。列表中的等待同步、同步中、已同步或失败状态，帮助使用者区分“修改已保存”和“索引已经更新”。

正常维护走增量同步：未变化内容尽量跳过，已有同模型文本向量可以复用，新增文本才需要编码；只修改阈值时主要更新索引属性。外部服务暂时失败时，任务保留状态并重试。

手动点击 同步 也会提交后台检查任务。更换 Embedding 模型或迁移向量集合时，则需要按迁移要求使用全量重建，并重新验证阈值。

这套设计让配置保存无需一直等待外部向量服务，也要求界面清楚展示更新进度。当前后台执行器采用单 worker；同一数据库的多实例调度仍需要额外设计。

查看日志：找到一次请求为什么这样返回

进入 日志 → 路由记录，可以按输入关键词或 Request ID 查找请求。打开详情后，可以看到输入全文、阶段耗时、候选判断、兜底过程和最终响应，还能跳转到关联运行日志。

图 6：路由记录详情：拆分输入向量化、正负例检索、排除判断和候选排序的耗时。

例如，普通物流查询这次请求的日志记录了负例排除，也拆开了 Embedding、正负检索和排序的耗时。排查时既可以问“为什么选了这个能力”，也可以问“时间花在了哪里”。

正负例检索可能并行，因此阶段占比不能简单相加；截图中的单次耗时也只代表当时请求。日志的价值在于提供定位依据，帮助后续优化有据可循。

让业务系统调用路由能力

网页适合配置和验证，实际集成通过 API 完成。外部预测使用独立的预测密钥，与管理台登录凭据分开。以默认后端端口为例：

接口返回匹配列表，包含 id、name、route_key、score 和 match_source 等字段。上层系统根据路由键选择能力，继续处理业务参数、权限和执行结果。

普通匹配没有合格结果时，还可以在设置中开启可选的大模型兜底。该路径召回候选职责，再让模型判断是否适用，允许匹配、拒绝或返回歧义；超时或无效输出保留默认处理。兜底结果会标明来源，避免把模型判断伪装成向量相似度分数。

这个项目中我关注的实现重点

我围绕语义路由服务和管理台完成开发，将能力配置、在线验证、反馈诊断与索引维护组织成一条使用链路。实现中重点处理了三个问题：

  • 怎样表达能力边界： 结合正负样本、独立阈值和启用状态筛选候选，保留可解释的返回结果。
  • 怎样维护配置与索引： 以 SQLite 为业务依据，通过持久化任务、版本检查、内容哈希和失败重试推进增量同步。
  • 怎样定位效果和时延问题： 提供在线测试、重叠诊断、请求过程记录与阶段耗时，支持用具体请求检查调整结果。

当前版本面向单工作区。对于新能力集合，仍需要准备独立的验证输入，覆盖清晰意图、相近意图、无匹配和歧义，才能判断实际质量。

使用 Intent Hub 时，可以先从两三个边界清楚的能力开始：配置职责和样本，完成同步，用真实表达测试，再接入上层应用。随着能力增加，继续通过反馈和诊断维护这份可运行的能力目录。
