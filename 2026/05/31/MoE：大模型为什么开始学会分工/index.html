MoE：大模型为什么开始学会分工

发表于2026-05-31|更新于2026-05-31|果冻的理论学习
|总字数:3.9k|阅读时长:13分钟

写在前面

最近学习大模型架构时，反复看到一个词：MoE，也就是 Mixture of Experts，专家混合。

它经常和 DeepSeek、Mixtral、Switch Transformer 这些模型一起出现。最吸引人的地方是：一个模型可以拥有非常大的总参数量，但每次推理时只激活其中一小部分参数。

比如 Mixtral 8x7B 的每个 MoE 层有 8 个专家，但每个 token 只选 2 个专家；DeepSeek-V2 的总参数是 236B，但每个 token 激活约 21B 参数；DeepSeek-V3 的总参数是 671B，每个 token 激活约 37B 参数。

所以 MoE 最有意思的问题不是“它是不是更大”，而是：

能不能让模型拥有更大的知识容量，同时不让每次推理的计算成本同比例暴涨？

这篇文章是我对 MoE 的一次系统学习整理。相比只把它理解成“多个专家一起工作”，我更愿意把 MoE 看成一种大模型内部的组织方式：用 Router 把 token 分配给不同专家，用稀疏激活把模型容量和计算成本部分解耦。

1. 从 dense FFN 到 MoE FFN

Transformer 里有两个很重要的子模块：Attention 和 FFN。

Attention 负责让 token 之间交换信息，FFN 则负责对每个 token 的隐藏状态做非线性变换。很多大语言模型里，FFN 占了相当大比例的参数。

也就是说，MoE 通常不是把整个模型复制很多份，而是把 Transformer block 里的 FFN 子层替换成一个“专家池”。

从这个角度看，MoE 的比喻可以是一个医院分诊系统：

  • token 先来到 Router；
  • Router 判断它更适合交给哪些专家；
  • 只调用少数几个 expert；
  • 最后把专家输出合并回主干网络。

这里有一个容易误解的点：Expert 通常不是一个完整大模型，而是一个 FFN/MLP 子网络。所以 MoE 不是“多个模型投票”，而是在模型内部引入了条件计算。

2. MoE 的核心：总参数和激活参数分离

理解 MoE，一定要分清两个数字：

指标 含义 为什么重要
总参数量 模型里一共有多少参数 代表模型容量，能容纳更多知识和模式
激活参数量 每个 token 实际参与计算的参数 更接近推理成本、吞吐和延迟

Dense model 的特点是：总参数量大致等于每次会用到的参数量。一个 70B dense 模型，每个 token 基本都要经过这 70B 参数对应的计算路径。

MoE 的特点是：总参数量可以很大，但每个 token 只激活少数专家。这样模型容量上去了，单 token 的计算量没有按总参数量线性增长。

这就是 MoE 的关键卖点：用稀疏激活换更大的模型容量。

Shazeer 等人在 2017 年的 Sparsely-Gated MoE 论文里，已经把这个方向说得很清楚：神经网络吸收知识的能力受参数数量限制，而条件计算可以让每个样本只激活网络的一部分，从而扩大容量又控制计算量。

  • 计算成本：只跑少数专家，下降明显；
  • 存储成本：专家参数仍然要放在设备上；
  • 通信成本：token 要被送到对应专家，分布式场景会更复杂；
  • 调度成本：专家负载不均会影响吞吐。

4. Dispatch 和 Combine：MoE 不是简单调用函数

从概念上看，Router 选择专家很简单。但在真实训练和推理里，MoE 层会经历两个额外步骤：

  • Dispatch：把 token 按照 Router 结果分发到对应专家；
  • Combine：把专家输出按 Router 权重合并回来，并恢复原来的 token 顺序。

这一步会引出很多工程问题。

假设一个 batch 里有 4096 个 token，8 个专家，每个 token 选 2 个专家。理论上会产生 8192 次 token-expert 分配。但这些分配不一定均匀，有些专家可能收到 1500 个 token，有些专家可能只收到 300 个 token。

这会导致两个后果：

  1. 热门专家成为瓶颈，整个 MoE 层要等它算完；
  2. 冷门专家训练不足，模型容量没有被充分使用。

所以 MoE 不只是“选择专家”，还要解决“如何把 token 高效地搬过去，再高效地搬回来”。

5. Capacity Factor：专家不是无限接诊

MoE 论文里经常出现一个概念：expert capacity。

直觉上，每个专家在一个 batch 里最多能处理多少 token，是需要提前规划的。因为 GPU 上通常希望张量形状稳定，不能每个 step 都让某个专家突然接收任意数量的 token。

一个常见写法是：

如果 capacity_factor = 1.25，说明每个专家预留比平均负载多 25% 的容量。

这会带来一个 tradeoff：

capacity factor 好处 代价
太小 计算更紧凑，浪费少 容易 token overflow，被丢弃或走备用路径
太大 更少 overflow，训练更稳定 padding 更多，计算和显存浪费更大

早期 MoE 和 Switch Transformer 都很重视这个问题。因为一旦专家容量不够，某些 token 的专家路径就会被截断，这会影响训练信号，也会让模型行为更难分析。

6. 负载均衡：让专家真的学会分工

MoE 最理想的状态，是不同专家形成有意义的 specialization。

但这个目标不是自然发生的。Router 可能会偷懒，总把 token 分给少数几个专家。于是很多 MoE 模型会引入负载均衡辅助损失，让每个专家收到的 token 数量更接近，同时也让 Router 的概率分布不要过度偏向少数专家。

但这里也有一个很微妙的问题：负载均衡损失是辅助目标，不能压过主任务目标。

如果辅助损失太弱，专家会失衡；如果辅助损失太强，Router 可能为了均匀而牺牲语义上更合理的专家选择。

DeepSeek-V3 里提出了 auxiliary-loss-free load balancing。我的理解是，它想绕开“辅助损失干扰主目标”的问题，通过动态 bias 等方式调节专家负载，而不是简单把一个很强的均衡损失加到训练目标里。

这说明 MoE 的研究重点已经从“多放几个专家”进入到更细的阶段：如何让专家高效、稳定、有分工地被使用。

7. top-1、top-2、共享专家：几种典型路由形态

不同 MoE 模型的 Router 设计差异很大。下面这张表可以帮助建立一个直觉。

路由形态 代表模型 特点 主要权衡
top-1 routing Switch Transformer 每个 token 只选 1 个专家 通信和计算简单，但单 token 的表达路径更窄
top-2 routing GShard、Mixtral 每个 token 选 2 个专家并加权合并 表达更丰富，但通信和计算更重
shared expert + routed experts DeepSeekMoE、DeepSeek-V2/V3 通用能力走共享专家，专门能力走路由专家 结构更复杂，但能减少专家间冗余
fine-grained experts DeepSeekMoE 把专家切得更细，给 Router 更多组合空间 对路由和负载均衡要求更高

Switch Transformer 的思路是把 MoE 简化到极致。top-1 routing 减少了通信和计算复杂度，也更容易扩展到超大参数规模。

Mixtral 采用 top-2 routing，每个 token 在每层选两个专家。它的优势是每个 token 有更丰富的专家组合，但服务系统要处理更多 token-expert 分发。

DeepSeekMoE 则进一步强调专家专精。它把专家切得更细，并引入共享专家。共享专家负责常见模式，路由专家负责更细分的知识或能力。

8. 分布式 MoE：瓶颈经常不在矩阵乘法

在单机上理解 MoE，容易以为它只是多了几个 FFN。真正的大规模 MoE 通常是多机多卡训练和推理，这时问题会变成系统工程。

如果专家分布在不同 GPU 上，Router 选完专家后，token 需要跨设备发送到对应专家。专家算完后，结果还要发回原来的位置。这类通信通常被称为 all-to-all。

这就解释了为什么 MoE 的“计算省了”不等于“整体一定更便宜”。

在大规模部署里，MoE 的性能取决于很多因素：

  • 专家如何放置在不同 GPU 上；
  • token dispatch 是否均匀；
  • all-to-all 通信带宽是否足够；
  • batch size 是否能填满专家容量；
  • Router 是否造成热点专家；
  • 推理框架能否高效做 expert parallelism。

所以比较 MoE 和 dense model 时，只看总参数量很容易误判。更合理的比较维度至少包括：

  • active parameters；
  • tokens/s；
  • 首 token 延迟和解码延迟；
  • 显存占用；
  • 网络通信；
  • batch size；
  • 训练稳定性；
  • 下游任务质量；
  • 单位 token 服务成本。

9. DeepSeekMoE：为什么说它在追求“专家更像专家”

DeepSeekMoE 的标题是 Towards Ultimate Expert Specialization in Mixture-of-Experts Language Models，关键词就是 specialization。

它关注的不是“有没有专家”，而是“专家是否真的专门化”。

传统 MoE 可能遇到一个问题：专家数量变多了，但专家之间学到的东西高度重叠。这样总参数虽然增加了，有效容量却没有充分释放。

DeepSeekMoE 的思路可以拆成两点：

9.1 更细粒度的 routed experts

如果每个专家很大，Router 的组合空间有限，专家之间也更容易学到重叠内容。

DeepSeekMoE 把专家切得更细。这样每个 token 可以从更多细粒度专家中组合出一条路径。直觉上，这更像从“几个大部门”变成“许多小团队”，Router 可以做更灵活的任务分配。

9.2 shared experts 承担通用能力

很多 token 都需要通用能力，比如语法、常识、基本表达、常见实体知识。如果这些通用模式让所有 routed experts 重复学习，就会浪费专家容量。

共享专家的作用，是把这部分通用能力单独承接下来。这样 routed experts 可以更专注于差异化知识。

这也是我觉得 DeepSeekMoE 比普通 MoE 更值得关注的地方：它不是只追求“参数更多”，而是在思考专家系统内部如何减少冗余、增强分工。

10. MoE 和 dense model 的真实取舍

MoE 听起来很诱人，但它不是 dense model 的简单替代品。

Dense model 的优势是：

  • 结构简单；
  • 训练更稳定；
  • 推理路径固定；
  • 部署和量化更成熟；
  • 小 batch 或低并发场景更容易做到低延迟。

MoE model 的优势是：

  • 总容量更大；
  • 每个 token 激活参数更少；
  • 高吞吐服务场景可能更划算；
  • 多领域、多任务、多语言场景可能更容易形成专家分工。

我的理解是，MoE 更适合“大规模训练 + 高并发服务 + 强工程能力”的场景。对于小模型、本地模型、低并发服务，MoE 未必比 dense 更合适。

一个很实用的判断方式是：不要问“这个模型有多少总参数”，而要问：

在我的推理框架、硬件、batch size、延迟要求下，它的 active parameters 和通信开销是否真的划算？

11. 一个从输入到输出的完整 MoE 心智模型

把前面的内容串起来，一个 MoE 层大概可以这样理解：

  1. 每个 token 进入 Transformer block；
  2. Attention 更新 token 的上下文表示；
  3. Router 根据 token hidden state 计算 expert score；
  4. 选择 top-k experts；
  5. Dispatch 把 token 发给对应专家；
  6. 每个 expert 对收到的 token 做 FFN 计算；
  7. Combine 按 Router 权重合并专家输出；
  8. 输出回到 Transformer 主干；
  9. 训练时额外处理负载均衡、容量限制和通信效率问题。

这比“专家混合”四个字复杂得多。MoE 的本质不是“混合”，而是“路由 + 稀疏计算 + 分布式调度 + 专家专精”。

12. 读 MoE 论文时可以抓住这几个问题

以后再看到一个 MoE 模型，我会优先看这些信息：

  1. 它有多少总参数？每个 token 激活多少参数？
  2. MoE 层替换的是哪些 FFN？是每层都有 MoE，还是部分层有？
  3. 每层有多少专家？每个 token 选几个专家？
  4. Router 是 top-1、top-2，还是更复杂的路由？
  5. 有没有 shared experts？
  6. 是否使用 fine-grained experts？
  7. 如何做 load balancing？
  8. capacity factor 是多少？overflow token 怎么处理？
  9. 专家并行和 all-to-all 通信怎么处理？
  10. 和同等推理成本的 dense model 相比，收益是否真实？

只要把这些问题问清楚，就不会被“几百 B 参数”这种数字牵着走。

13. 我现在如何理解 MoE

学完之后，我觉得 MoE 最好不要被理解成“模型变大的一种偷懒方法”。

它更像是大模型架构里的一次组织方式变化：

  • dense model 是所有 token 共享同一套参数路径；
  • MoE 是给模型内部引入分工机制；
  • Router 负责决定任务交给谁；
  • Expert 负责在自己的子空间里提升能力；
  • 稀疏激活负责控制计算成本；
  • 分布式系统负责把这套机制真正跑快。

但它不是万能答案。MoE 的代价来自通信、调度、容量管理、训练稳定性和部署复杂度。

所以我会用一句话总结 MoE：

MoE 的本质，是用“按 token 分工”的方式，把模型容量和计算成本部分解耦；它用架构复杂度和系统复杂度，换取更大的参数容量和潜在更高的服务效率。
